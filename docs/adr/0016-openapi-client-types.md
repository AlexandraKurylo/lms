# ADR 0016 — Типи клієнта генеруються зі специфікації OpenAPI

**Статус:** прийнято, 2026-10-28.

## Контекст

Файл `client/src/shared/api/types.ts` вручну повторював форми відповідей API (понад 240 рядків). Кожна зміна
специфікації `openapi/openapi.yaml` вимагала окремої правки в клієнті, і ніщо не нагадувало про розбіжність:
поле, перейменоване в API, ламалося б лише під час роботи застосунку. Специфікація при цьому вже є документом
контракту (Swagger UI, `api:lint`), тобто той самий опис існує двічі.

## Розглянуті варіанти

1. **Писати типи вручну (як було).** Нічого не додається, але два описи одного контракту розходяться непомітно.
2. **Генерувати типи зі специфікації (`openapi-typescript`).** Специфікація стає єдиним джерелом, а розбіжність
   стає помилкою компіляції клієнта.
3. **Генерувати специфікацію зі схем zod на сервері.** Контракт тоді завжди збігається з кодом сервера, але
   потрібна бібліотека, яка перетворює zod 4 на OpenAPI, а вже написану й перевірену специфікацію довелося б
   переробляти.
4. **Спільний пакет типів для сервера й клієнта (монорепозиторій).** Типи не розходяться, але змінюється вся
   структура репозиторію й складання Docker-образів.

## Рішення

Варіант 2. Скрипт `npm run api:types` у `client` перетворює `openapi/openapi.yaml` на
`src/shared/api/schema.d.ts`; файл зберігається в репозиторії. `types.ts` лише перейменовує потрібні схеми
(`Schemas['Course…']`), тому решта коду клієнта імпортує ті самі імена, що й раніше. У CI крок
`npm run api:types:check` генерує файл заново й падає, якщо результат відрізняється від збереженого.

## Наслідки

- (+) Зміна специфікації без перегенерації типів не проходить CI; зміна контракту видна в діффі `schema.d.ts`.
- (+) Клієнтські типи не можна забути оновити, а їх опис не дублюється.
- (−) Типи описують те, що сказано в специфікації, а не те, що фактично повертає сервер: відповідність відповідей
  сервера специфікації перевіряють лише тести на коректність посилань і коди помилок.
- (−) Тіла запитів із необов'язковими полями дають необов'язкові поля в типі; форми клієнта, яким потрібні всі
  значення, обгортають такий тип у `Required<…>`.
- (−) З'являється згенерований файл, який не слід правити вручну.

## Умова перегляду

Якщо специфікація та сервер почнуть розходитися, а ручна синхронізація стане джерелом помилок, переходимо до
варіанту 3 (специфікація з коду) або додаємо перевірку відповідей сервера за схемою.
