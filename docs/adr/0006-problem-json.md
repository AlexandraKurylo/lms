# ADR 0006 — помилки API у форматі problem+json

**Статус:** прийнято, 2026-10-17.

## Контекст

Клієнт має відрізняти помилки програмно: «місць немає» показується одним повідомленням, «урок закритий» —
іншим, «email зайнятий» підсвічує поле форми. Розбирати для цього текст повідомлення ненадійно:
текст змінюється, перекладається, містить деталі. Окремо методичка (п. 5.4) вимагає формат RFC 9457,
стабільний `type`, обґрунтовані коди станів і відсутність стектрейсу у відповіді 500.

## Розглянуті варіанти

1. **Власний формат** `{ "error": "текст" }`. Просто, але немає стабільного ідентифікатора помилки,
   кожен клієнт вигадує свою розбірку тексту.
2. **`application/problem+json` (RFC 9457)** зі стабільним полем `type`, `title`, `status`, `detail`
   і розширеннями `requestId` та `errors[]` для полів форми.

## Рішення

Усі помилки, включно з 404 невідомого маршруту й 500, повертаються як `application/problem+json`.
`type` має вигляд `https://lms.example/problems/<код>` і ніколи не змінюється; `title` — короткий
заголовок для людини; `requestId` збігається із заголовком `X-Request-Id` та рядками логу.
Бізнес-логіка кидає `DomainError(код)`, а відповідність «код → HTTP-статус» живе лише в HTTP-шарі
(`shared/problem.ts`).

Обрані коди станів:

| Клас помилки                                                                                                                  | Статус | Чому                                                                     |
| ----------------------------------------------------------------------------------------------------------------------------- | ------ | ------------------------------------------------------------------------ |
| `validation`, `bad-request`                                                                                                   | 400    | запит синтаксично чи за схемою некоректний                               |
| `unauthorized`, `invalid-credentials`                                                                                         | 401    | немає або невірні облікові дані                                          |
| `forbidden`, `lesson-locked`, `not-enrolled`                                                                                  | 403    | користувач відомий, але дія йому не дозволена                            |
| `not-found`                                                                                                                   | 404    | ресурсу немає **або він чужий** — так ми не підтверджуємо його існування |
| `email-taken`, `already-enrolled`, `stream-full`, `stream-closed`, `has-later-progress`, `course-in-use`, `course-incomplete` | 409    | запит коректний, але конфліктує зі станом даних                          |
| `payload-too-large`                                                                                                           | 413    | перевищено ліміт тіла запиту або файлу                                   |
| `idempotency-key-reuse`                                                                                                       | 422    | той самий `Idempotency-Key` із іншим вмістом запиту                      |
| `rate-limited`                                                                                                                | 429    | перевищено ліміт спроб                                                   |
| `internal`                                                                                                                    | 500    | наша помилка; відповідь без `detail` і стектрейсу                        |
| `service-unavailable`                                                                                                         | 503    | залежність (БД) недоступна                                               |

## Наслідки

- (+) Клієнт перемикається за `type`, а не за текстом; повідомлення для користувача можна змінювати вільно.
- (+) 500 нічого не розкриває: ні тексту помилки, ні шляхів, ні SQL; докладності лишаються в логах за `requestId`.
- (+) Спеціальний 404 для чужих ресурсів не дає з'ясувати, чи існує ресурс.
- (−) Кожен новий клас помилки треба додати в `PROBLEMS`, у специфікацію OpenAPI і в цю таблицю.
- (−) Ми використовуємо 409 для всіх конфліктів стану; клієнт має дивитися саме на `type`.

## Умова перегляду

Якщо з'являться зовнішні клієнти, які очікують інший формат помилок, додаємо серіалізатор для нього,
а внутрішній формат лишаємо.
