# ADR 0013 — Чужий ресурс: 404, а не 403

**Статус:** прийнято, 2026-10-18.

## Контекст

У кабінеті викладача є три різні причини відмовити:

1. немає сесії;
2. сесія є, але роль не підходить (студент у кабінеті викладача);
3. роль підходить, але курс належить іншому викладачеві.

Для кожної треба вибрати відповідь, яка не видає зайвого.

## Розглянуті варіанти для випадку 3

1. **403 Forbidden.** Чесно, але відповідь підтверджує, що курс з таким id існує. Перебираючи id, можна
   скласти список чужих курсів.
2. **404 Not Found.** Чужий курс виглядає так само, як неіснуючий.

## Рішення

- немає сесії → **401**;
- роль не `teacher`/`admin` → **403** (`requireRole` на весь роутер `/api/teacher`). Тут
  розкривати нічого: «студентам сюди не можна» відомо всім;
- курс чужий → **404**, ідентичний відповіді на неіснуючий курс (той самий `type` і `detail`; це перевіряє тест).

Перевірка власника робиться **в умові запиту до БД**, а не окремим кроком у коді:

```ts
db.course.updateMany({ where: { id, teacherId: user.id }, data })   // count === 0 → 404
```

Бо «прочитати курс → порівняти власника → записати» має проміжок, у якому стан може змінитися. Єдиний
`UPDATE ... WHERE id = ? AND teacher_id = ?` атомарний. Умова збирається в одному місці, `scopeFor(user)`:
адміністратор отримує порожню умову (бачить усе), викладач — `{ teacherId }`.

Власник береться лише із сесії. У схемах тіла запиту поля `teacherId` немає, а `.strict()` відхиляє зайві поля з
400, тому «створити курс від імені іншого» неможливо.

## Наслідки

- (+) Не можна дізнатися, які id існують і кому належать.
- (+) Правило власника живе в одному файлі; новий маршрут кабінету бере його звідти.
- (−) Налагоджувати складніше: 404 може означати і «немає», і «чуже». Причину видно в логах за `requestId`
  і користувачем сесії.
- (−) Для публічного ресурсу (каталог) цей принцип не потрібен: чернетка там теж дає 404 (див. OpenAPI).
