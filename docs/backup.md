# Резервне копіювання та відновлення

Що копіюється:

| Дані                                                 | Де живуть                                 | Файл копії              |
| ---------------------------------------------------- | ----------------------------------------- | ----------------------- |
| База PostgreSQL (усі 12 таблиць)                     | контейнер `db`, volume `lms_pgdata`       | `lms-<час>.dump`        |
| Файли матеріалів і домашніх робіт                    | volume `lms_uploads` або `server/uploads` | `lms-<час>-uploads.tgz` |
| Кількість рядків, індексів, обмежень на момент копії | обчислюється під час копіювання           | `lms-<час>.stats`       |
| Контрольні суми                                      |                                           | `lms-<час>.sha256`      |

Копії лежать у каталозі `backups/` (він у `.gitignore`). У них є пошти та хеші паролів, тому каталог створюється
з правами `700`, а файли з `600`. Не публікуйте їх і не додавайте до репозиторію.

## Вимоги

Скрипти написані на TypeScript і запускаються командами `npm run` з каталогу `server`, тож працюють однаково
в Windows, macOS і Linux. Потрібні Node.js 22, встановлені залежності (`npm ci`) і Docker Desktop із запущеною
базою (`docker compose up -d`). Для архівування файлів використовується системна команда `tar` (є в Windows 10+).

## Зробити копію

```bash
cd server
npm run db:backup
```

Скрипт читає `.env`, робить `pg_dump`, архівує файли користувачів, рахує контрольні суми й видаляє копії,
старші за останні `BACKUP_KEEP` (за замовчуванням 7).

## Перевірити, що копію можна відновити

```bash
npm run db:verify                              # найновіша копія
npm run db:verify -- ../backups/lms-….dump     # конкретна копія
```

Скрипт створює тимчасову базу `lms_restore_check`, відновлює в неї копію, порівнює кількість рядків, індексів і
обмежень зі збереженими на момент копіювання, перевіряє, що кожен файл, на який посилається база, є в архіві, і
видаляє тимчасову базу. Робоча база не змінюється. Код виходу 0 означає, що копія придатна.

Якщо під час копіювання в базу йшли записи, кількість рядків може трохи відрізнятися. Тоді `db:backup` позначає
`.stats` рядком `# drift`, а `db:verify` лише попереджає про різницю в кількості рядків. Розбіжність індексів чи
обмежень, пошкоджений файл і відсутні файли користувачів завжди вважаються помилкою.

## Відновити

```bash
npm run db:restore                               # найновіша копія
npm run db:restore -- ../backups/lms-….dump      # конкретна копія
npm run db:restore -- --yes                      # без запитання
npm run db:restore -- --no-uploads               # лише база
```

Скрипт перевіряє контрольні суми, просить ввести «так» (поточні дані буде видалено), зупиняє `web` і `api`,
перестворює базу, відновлює дані й файли, порівнює результат зі `.stats` і знову запускає `api` та `web`.

## Автоматичний запуск

Щодоби о 03:00 з перевіркою відновлення (Linux, macOS):

```cron
0 3 * * * cd /шлях/до/lms/server && npm run db:backup >> ../backups/backup.log 2>&1 && npm run db:verify >> ../backups/backup.log 2>&1
```

У Windows те саме робить Планувальник завдань: програма `cmd`, аргументи `/c "cd /d C:\шлях\до\lms\server && npm run db:backup && npm run db:verify"`.

## Налаштування

| Змінна                | За замовчуванням        | Призначення                                                                                                                                                                                                                                                             |
| --------------------- | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BACKUP_MODE`         | `docker`                | `docker` працює через контейнер `db`; `local` через клієнт PostgreSQL на машині (потрібні `psql`, `pg_dump`, `pg_restore` і `DATABASE_URL`)                                                                                                                             |
| `BACKUP_DIR`          | `./backups`             | куди писати копії                                                                                                                                                                                                                                                       |
| `BACKUP_KEEP`         | `7`                     | скільки останніх копій зберігати (`0` вимикає видалення)                                                                                                                                                                                                                |
| `UPLOADS_SOURCE`      | `auto`                  | де лежать файли користувачів: `volume` (контейнер `api`, volume `lms_uploads`) або `dir` (каталог `UPLOAD_DIR`, коли API запущено локально через `npm run dev`). За замовчуванням: `volume`, якщо контейнер `api` працює, а каталог `UPLOAD_DIR` порожній, інакше `dir` |
| `UPLOADS_VOLUME`      | знаходиться автоматично | назва volume з файлами, якщо автопошук не спрацював                                                                                                                                                                                                                     |
| `BACKUP_HELPER_IMAGE` | `postgres:16-alpine`    | образ, у якому виконується `tar` для volume (вже завантажений для бази)                                                                                                                                                                                                 |

## Результат перевірки на демо-даних

Перевірено на базі після сиду (211 користувачів, 40 курсів, 500 уроків, 800 записів, 989 матеріалів, 416 домашніх
робіт; 12 таблиць, 33 індекси, 45 обмежень) і двох файлах користувачів, режим `local`:

| Перевірка                                                                                                | Результат                                              |
| -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| Копія бази й файлів                                                                                      | 0,7 с, файл `.dump` 252 КБ                             |
| `db:verify`: усі таблиці, індекси, обмеження збіглися                                                    | пройдено                                               |
| Імітація аварії (видалено записи, домашні роботи, матеріали, 200 студентів і файли) і `restore.sh --yes` | дані й файли відновлено за 0,7 с, `db:verify` пройдено |
| Пошкоджений байт у `.dump`                                                                               | відхилено за контрольною сумою, код виходу 1           |
| Відсутній у архіві файл, на який посилається база                                                        | `db:verify` повідомляє розбіжність, код 1              |
| Відмова на запитання підтвердження                                                                       | нічого не змінено, код 1                               |
| Видалення старих копій при `BACKUP_KEEP=2`                                                               | залишилось дві найновіші                               |

Режим `docker` перевірено лише на рівні складання команд: повний прогін із Docker Desktop виконайте самостійно за інструкцією вище.

## Обмеження

- Цільова точка відновлення (RPO) дорівнює інтервалу між копіями: за щодобового розкладу можна втратити до доби даних.
- База й файли копіюються послідовно, не атомарно; `db:verify` покаже, якщо в базі є посилання на файл, якого немає в архіві.
- Копії лежать на тій самій машині. Для захисту від її втрати періодично переносьте `backups/` на інший диск або
  у хмарне сховище.

Обґрунтування рішення: [ADR 0015](adr/0015-backups.md).
