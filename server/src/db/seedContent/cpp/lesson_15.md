# Урок 15. Словник із пошуком, що не гальмує

## Пролог: лінійний пошук — це нормально (поки що)

Уяви, що в тебе словник на 50 слів. Користувач шукає «dharma». Ти береш перше слово — «не те», береш друге — «не те», третє — «не те», двадцять третє — «О, ОСЬ!» У середньому — 25 порівнянь. Користувач навіть не помітив. Тепер уяви 50 000 слів. Середнє — 25 000 порівнянь. Користувач уже бачить затримку. А якщо це мобільний застосунок на старому телефоні — затримка відчутна.

Сьогодні ми розберемося, як зробити пошук швидким незалежно від розміру словника. Рішень кілька, і кожне має свої компроміси. Почнемо з найпростішого — лінійного пошуку, бо для нашого SAMSKRTA на старті його вистачить. Потім подивимося на бінарний пошук (якщо дані відсортовані), хеш-таблиці (миттєвий пошук) і префіксні дерева (для автодоповнення).

## Код уроку

Урок дає застосунку файл, обіцяний ще в уроці 9: `src/search/WordIndex.h`. Досі `Database` зберігала слова простим вектором, і щоб знайти слово, довелося б перебирати всі. Тепер поруч зі сховищем з'явиться **індекс** — і саме слово «індекс» тут означає рівно те саме, що в базах даних.

```cpp
// src/search/WordIndex.h
// Словник із пошуком, що не залежить від кількості слів.
// Заголовок. Сам по собі не збирається — його підключають інші файли.
#pragma once

#include <string>
#include <unordered_map>
#include <vector>
#include "../domain/Word.h"

class WordIndex {
public:
    // Додати слово. Індекс оновлюється разом зі сховищем — інакше
    // вони розійдуться, і пошук почне брехати.
    void add(Word w) {
        m_byTranslit[w.transliteration] = m_words.size();
        m_words.push_back(std::move(w));
    }

    // Пошук за транслітерацією. Не залежить від розміру словника.
    const Word* find(const std::string& transliteration) const {
        auto it = m_byTranslit.find(transliteration);
        if (it == m_byTranslit.end()) return nullptr;
        return &m_words[it->second];
    }

    // Повний перебір лишається доступним: індекс його не замінює,
    // а доповнює. Порядок тут — той, у якому слова додавали.
    const std::vector<Word>& all() const { return m_words; }

    size_t size() const { return m_words.size(); }

    // Скільки пам'яті коштує сам індекс, без самих слів.
    size_t indexBuckets() const { return m_byTranslit.bucket_count(); }

private:
    std::vector<Word> m_words;                             // самі слова
    std::unordered_map<std::string, size_t> m_byTranslit;  // транслітерація -> номер
};
```

Зверни увагу на головне архітектурне рішення: у хеш-таблиці лежать **не слова, а їхні номери**. Слова живуть у векторі, як і раніше. Якби ми поклали в `unordered_map` самі `Word`, у нас було б дві копії кожного слова, а перебір у порядку додавання став би неможливим. Так само роблять справжні бази даних: дані в одному місці, індекс — окремо, і індексів може бути кілька на ту саму таблицю.

Тепер перевіримо, чи взагалі варта ця складність заходу. Вправа `exercises/ex15_bench.cpp` порівнює чотири способи знайти слово у словнику зі ста тисяч записів. Один важливий нюанс збірки:

```cmake
add_executable(ex15_bench  exercises/ex15_bench.cpp)
target_compile_options(ex15_bench PRIVATE $<$<CONFIG:Release>:-O2>)
```

Заміри без оптимізації не варті нічого: у налагоджувальній збірці стандартна бібліотека працює в кілька разів повільніше й зовсім не так, як у справжній програмі. Збирай `ex15_bench` тільки в Release.

```cpp
// exercises/ex15_bench.cpp — серцевина; повний файл лежить у проєкті

const Word* linearSearch(const std::vector<Word>& dict, const std::string& query) {
    for (const auto& w : dict) {
        if (w.transliteration == query) return &w;
    }
    return nullptr;
}

const Word* binarySearch(const std::vector<Word>& dict, const std::string& query) {
    auto it = std::lower_bound(dict.begin(), dict.end(), query,
        [](const Word& w, const std::string& q) {
            return w.transliteration < q;
        });
    if (it != dict.end() && it->transliteration == query) return &*it;
    return nullptr;
}

template <typename Func>
double measureMs(Func f) {
    auto start = std::chrono::steady_clock::now();
    f();
    auto end = std::chrono::steady_clock::now();
    return std::chrono::duration<double, std::milli>(end - start).count();
}

int main() {
    const size_t N = 100000;
    const int QUERIES = 1000;

    auto dict = makeTestDict(N);           // 100 000 слів, відсортованих
    WordIndex index;
    for (const auto& w : dict) index.add(w);

    volatile size_t found = 0;   // volatile, щоб оптимізатор не викинув пошук

    double tLinear = measureMs([&] {
        for (const auto& q : queries) if (linearSearch(dict, q)) ++found;
    });
    double tHash = measureMs([&] {
        for (const auto& q : queries) if (index.find(q)) ++found;
    });
    // ... те саме для бінарного пошуку і std::map
}
```

Конкретні числа в тебе будуть інші — вони залежать від процесора, і навіть на одній машині гуляють від запуску до запуску (у мене співвідношення виходило то 1469, то 2109 разів). Значення має не число, а **порядок величини**: різниця між лінійним пошуком і рештою — три порядки, а між бінарним, деревом і хешем — у межах одного.

Ось що з цього справді варто винести.

**Лінійний пошук коштує 268 мікросекунд на один запит.** Це виглядає як «нічого», поки не згадаєш, що інтерфейс перемальовується 60 разів на секунду, тобто на кадр є 16 мілісекунд. Шістдесят таких пошуків за кадр — і застосунок почне помітно підгальмовувати на порожньому місці. Саме так і виглядає більшість «незрозумілих гальм» у програмах: не одна повільна операція, а тисяча швидких.

**Бінарний пошук програє хешу всього втричі, а не в тисячу разів.** Це важливо, бо `O(log n)` проти `O(1)` на папері виглядає як прірва. Для ста тисяч елементів `log₂(100000)` ≈ 17 порівнянь — і сімнадцять порівнянь рядків справді коштують стільки ж, скільки одне обчислення хеша плюс один похід у пам'ять. Прірва з'явилася б на мільярді записів, а не на ста тисячах.

**`std::map` вдвічі повільніший за `unordered_map`, хоча складність та сама.** Причина не в алгоритмі, а в пам'яті: дерево розкидане по купі окремими вузлами, і кожен крок пошуку — це стрибок у нове місце, майже завжди повз кеш процесора. Вектор і хеш-таблиця лежать суцільними шматками. Асимптотика не бачить кеша, а секундомір бачить.

**131 072 кошики на 100 000 слів.** Хеш-таблиця тримає більше кошиків, ніж елементів, щоб колізій було мало, — це і є ціна швидкості: близько третини зайвої пам'яті плюс сам масив індексів. `O(1)` не безкоштовна, вона куплена за пам'ять.

Розберемо решту.

**`std::lower_bound`** — алгоритм бінарного пошуку в **відсортованому** контейнері. Повертає ітератор на перший елемент, який **не менший** за запит. Якщо цей елемент дорівнює запиту — знайшли. Інакше — не знайшли. Бінарний пошук працює за `O(log n)`: для мільйона елементів — близько 20 порівнянь замість мільйона.

**`std::unordered_map`** — хеш-таблиця. Під капотом — масив «кошиків», у кожний з яких потрапляють елементи з однаковим хешем ключа. Пошук — обчислити хеш ключа, заглянути в потрібний кошик, порівняти. У середньому `O(1)`, у гіршому випадку (погана хеш-функція, багато колізій) — `O(n)`. Для коротких рядків типу «dharma» — ідеально. Для дуже довгих — може бути повільніше через обчислення хеша.

**`std::map`** — «впорядковане дерево» (зазвичай червоно-чорне). Кожен елемент зберігається у вузлі дерева, де лівий нащадок — менший, правий — більший. Пошук — `O(log n)`. Додаткова перевага: елементи завжди у відсортованому порядку, можна робити `lower_bound`/`upper_bound`, можна перебирати в алфавітному порядку. Якщо тобі потрібен порядок — `map`. Якщо ні — `unordered_map`.

**Лямбда як компаратор** — `[](const Word& a, const Word& b) { return a.transliteration < b.transliteration; }`. `std::sort` і `std::lower_bound` вимагають функцію порівняння, лямбда — найзручніший спосіб її дати.

**`std::chrono`** — стандартний спосіб виміряти час. Я взяв `steady_clock`, а не `high_resolution_clock`, і це не дрібниця: `steady_clock` гарантовано тільки йде вперед і не стрибає, якщо система переведе годинник (синхронізація часу, перехід на літній час). `high_resolution_clock` на MSVC — просто псевдонім до `steady_clock`, а на деяких інших реалізаціях — до `system_clock`, який стрибати може. Для вимірювання проміжків завжди бери `steady_clock`.

**`volatile size_t found`** — рядок, без якого весь тест був би брехнею. Оптимізатор бачить, що результат пошуку нікуди не використовується, і має повне право **викинути весь цикл**. Тоді ти виміряєш час порожньої програми й радісно доповіси, що хеш працює за нуль наносекунд. `volatile` забороняє компілятору викидати запис у цю змінну, і цикл лишається на місці. Це стандартна пастка всіх саморобних бенчмарків; у серйозних вимірюваннях беруть бібліотеку на кшталт Google Benchmark, де для цього є спеціальна функція `DoNotOptimize`.

**Запити згенеровані як `(i * 97) % N`, а не випадково.** Так тест відтворюваний від запуску до запуску, і при цьому звертання розкидані по всьому словнику: якби ми шукали слова підряд, кеш процесора підіграв би лінійному пошуку, і порівняння вийшло б нечесним на його користь.

## Де це реально використовується

**Chromium** використовує близько десятка різних контейнерів для різних задач: `std::unordered_map` для кешу URL, `base::flat_map` (свій аналог `std::map` поверх вектора) для невеликих колекцій, спеціальні дерева для DOM. Кожен вибір обґрунтований профілюванням.

**Бази даних** — це, по суті, дуже складні словники з пошуком. Індекс у SQL — це `std::map` або `std::unordered_map` під капотом. Коли ти пишеш `SELECT * FROM users WHERE name = 'John'`, база даних шукає у відповідному індексі — і різниця між лінійним пошуком і хешем тут та сама, що в нашому тесті: секунди проти мілісекунд.

**Англо-український словник** в якомусь додатку — класична задача пошуку. Якщо словник у пам'яті (а не в БД), то це `unordered_map<string, vector<Translation>>`. Значення — вектор, бо одне слово може мати кілька перекладів. Шукаєш за англійським — отримуєш усі варіанти українського. Швидко, ефективно.

**Автодоповнення** в Google Search — це не просто хеш-таблиця. Це **префіксне дерево** (trie, від retrieval) — структура даних, де кожен вузол відповідає одній літері, а шлях від кореня до вузла — префіксу якогось слова. Шукаєш «dev» — проходиш по дереву d → e → v, і отримуєш усі слова, що починаються на «dev»: dev, development, developer, deviate — рівно за стільки кроків, скільки літер у запиті, незалежно від розміру всього словника:

```cpp
struct TrieNode {
    std::unordered_map<char, std::unique_ptr<TrieNode>> children;
    std::vector<size_t> wordIndices;  // індекси слів, чий текст проходить через цей вузол
};

void insertWord(TrieNode& root, const std::string& text, size_t wordIndex) {
    TrieNode* node = &root;
    for (char c : text) {
        auto& child = node->children[c];
        if (!child) child = std::make_unique<TrieNode>();
        node = child.get();
        node->wordIndices.push_back(wordIndex);
    }
}

std::vector<size_t> searchPrefix(const TrieNode& root, const std::string& prefix) {
    const TrieNode* node = &root;
    for (char c : prefix) {
        auto it = node->children.find(c);
        if (it == node->children.end()) return {};  // такого префіксу немає взагалі
        node = it->second.get();
    }
    return node->wordIndices;
}
```

Список `wordIndices` навмисно зберігається в кожному вузлі на шляху, а не тільки в кінцевому — вузол, що відповідає префіксу «dha», уже знає індекси всіх слів, які починаються на ці три літери, і пошук закінчується прямо тут, без додаткового обходу піддерева. Дерево будується один раз при завантаженні словника, а не при кожному натисканні клавіші — у нашому SAMSKRTA автодоповнення транслітерації — це готова задача для trie.

**Аналогія з бібліотекою**: лінійний пошук — це коли бібліотекар обходить усі полиці в пошуках книги. Працює, але повільно. Бінарний — коли книги відсортовані за автором, і бібліотекар одразу йде до потрібної секції. Хеш-таблиця — коли в бібліотеці є каталог за роком видання, і бібліотекар знає, де шукати за роком. Map (дерево) — каталог за автором, де імена відсортовані алфавітом, і можна швидко переглянути в алфавітному порядку. Trie — коли ти хочеш знайти всі книги, що починаються на «Ко». У реальній бібліотеці використовують усі ці методи одночасно.

## Застосовуємо переможця до справжнього Database

Словник у нашому проєкті поки що крихітний, і лінійний перебір у `Database::allWords()` з уроку 9 непомітний. Але саме тому урок і має сенс пройти зараз, поки це не болить: додамо в `src/data/Database.h` індекс за транслітерацією, той самий `std::unordered_map`, що щойно виграв тест:

```cpp
// доповнення до Database з уроку 9
private:
    std::unordered_map<std::string, size_t> m_byTranslit;  // transliteration -> індекс у m_words

public:
    void addWord(Word word) {
        std::lock_guard<std::mutex> lock(m_mutex);
        word.id = ++m_nextId;
        m_byTranslit[word.transliteration] = m_words.size();
        m_words.push_back(std::move(word));
    }

    const Word* findByTransliteration(const std::string& translit) const {
        std::lock_guard<std::mutex> lock(m_mutex);
        auto it = m_byTranslit.find(translit);
        return (it != m_byTranslit.end()) ? &m_words[it->second] : nullptr;
    }
```

Один рядок у `addWord` і один новий метод — і пошук слова за транслітерацією більше не лінійний, незалежно від того, чи в словнику 10 слів, чи 100 000.

## Куди це веде далі

**Замість `std::unordered_map` для маленьких колекцій** — `std::vector` з бінарним пошуком. Для 100 елементів вектор швидший за хеш, бо не витрачає час на обчислення хеша. Правило: до ~50 елементів — вектор, далі — залежно від задачі.

**Замість std-контейнерів** — у Qt є `QHash` (аналог `unordered_map`), `QMap` (аналог `map`). Вони інтегровані з іншими типами Qt (`QString` як ключ — нативно). У Qt 6 можна використовувати обидва варіанти.

**Для автодоповнення** — `std::map` або trie (спеціальна структура). Trie дає `O(k)` пошук префікса, де `k` — довжина префікса. Ідеально для нашого SAMSKRTA, де ти вводиш «dha» і хочеш отримати «dharma», «dharaNa», тощо.
