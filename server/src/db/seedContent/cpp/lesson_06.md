# Урок 6. Рядки, де панує хаос

## Найнебезпечніше слово у програмуванні

Знаєш, яке найнебезпечніше слово в програмуванні? Не `goto`, не `volatile`, навіть не `delete`. Це слово **`"просто"`.** «Просто додай рядок», «просто виведи текст», «просто порівняй слова». Кожне «просто» в роботі з текстом — це потенційний тиждень дебагу через три місяці. Бо рядки — це не просто послідовність символів. Рядки — це **одна з найглибших ям** у програмуванні, особливо в C++, де історично склалося так, що до стандарту C++17 навіть не було нормального типу `std::string_view`.

У цьому уроці ми розберемося, як букви стали числами (коротко, бо інакше можна окрему книгу писати), чому `strlen("привіт")` повертає не 12, і як `std::string` намагається врятувати тебе від цього хаосу. А наступного разу — деванагарі, де хаос вибухне по-справжньому.

## Як букви стали числами: подорож у 90 секунд

Коли комп'ютери тільки народилися, інженери вирішили: кожному символу — число. Зробили таблицю ASCII: 128 символів, від 0 до 127. Латиниця, цифри, знаки пунктуації — все влазило. Слово `Hello` — це числа 72, 101, 108, 108, 111. Просто, зручно, вміщується в один байт.

Потім людям захотілося більше. Кирилиця, деванагарі, китайські ієроглíфи, емодзі 🚀 — усього цього в 128 комірках не влізе. Тоді придумали Unicode — величезну таблицю, де кожному символу планети дали унікальний номер («code point»). Наприклад, літера `А` — це U+0410, літера `अ` (деванагарі) — це U+0905, емодзі 🚀 — U+1F680. Номери доходять до понад мільйона.

А далі починається хаос: як ці номери зберігати в пам'яті? Тут виникло кілька «кодувань» — способів перетворити Unicode-номери в байти:

- **UTF-8**: 1–4 байти на символ. Латиниця — 1 байт (як у старому ASCII), кирилиця — 2 байти, деванагарі — 3 байти, емодзі — 4 байти. Економно, але рахувати «скільки символів у рядку» — біль.
- **UTF-16**: 2 або 4 байти на символ. Більшість — 2 байти, рідкісні — 4 (як емодзі). Використовується в Windows, Java, JavaScript. Швидко для більшості мов, але не для ASCII.
- **UTF-32**: завжди 4 байти на символ. Просто, але марнотратно: слово «Hello» займає 20 байт замість 5.

Веб-стандарт сьогодні — UTF-8. У C++ `std::string` за замовчуванням зберігає байти, а не символи. Якогось конкретного кодування він сам по собі не гарантує. Це означає, що `std::string` — це просто коробка з байтами, а що вони означають — вирішуєш ти і контекст.

## Код уроку

Четверта вправа в дереві проєкту — `exercises/ex06_strings.cpp`, рядок у `CMakeLists.txt` дописується так само:

```cmake
add_executable(ex06_strings  exercises/ex06_strings.cpp)
```

Дані тут уже не навчальні: це реальний запис нашого словника — слово письмом деванагарі, його транслітерація і переклад. Ті самі три рядки в уроці 8 стануть полями `devanagari`, `transliteration` і `translation` у структурі `Word`. Тому все, що ми зараз побачимо про байти, стосується не абстрактного тексту, а того, що лежатиме в кожному записі нашої бази.

```cpp
// exercises/ex06_strings.cpp
// Байти проти символів на власних даних словника.
// Збери разом із проєктом: cmake --build build
// Запусти:                 ./build/ex06_strings

#include <iostream>
#include <iomanip>
#include <string>
#include <string_view>   // C++17

// ===== Скільки в рядку code points =====
// В UTF-8 продовження багатобайтової послідовності завжди починається
// з бітів 10xxxxxx. Рахуємо байти, які НЕ є продовженням, — це й буде
// кількість code points.
int countCodePoints(const std::string& s) {
    int n = 0;
    for (unsigned char b : s) {
        if ((b & 0xC0) != 0x80) ++n;
    }
    return n;
}

int main() {
    // ===== Частина 1: size() рахує байти, а не символи =====
    std::string translit   = "dharma";   // латиниця
    std::string devanagari = "धर्म";       // те саме слово письмом деванагарі
    std::string ukrainian  = "закон";    // переклад

    std::cout << "рядок       байтів   code points\n";
    std::cout << "dharma        " << translit.size()
              << "        " << countCodePoints(translit) << "\n";
    std::cout << "धर्म           " << devanagari.size()
              << "        " << countCodePoints(devanagari) << "\n";
    std::cout << "закон         " << ukrainian.size()
              << "       " << countCodePoints(ukrainian) << "\n\n";

    // ===== Частина 2: з чого саме складаються ці байти =====
    std::cout << "байти \"" << devanagari << "\" у шістнадцятковому вигляді:\n  ";
    for (unsigned char b : devanagari) {
        std::cout << std::hex << std::uppercase << std::setw(2) << std::setfill('0')
                  << static_cast<int>(b) << " ";
    }
    std::cout << std::dec << std::nouppercase << std::setfill(' ') << "\n\n";

    // ===== Частина 3: substr ріже байти, а не літери =====
    std::string cut = devanagari.substr(0, 4);
    std::cout << "devanagari.substr(0, 4) дало " << cut.size()
              << " байти, і ось що з цього вийшло: \"" << cut << "\"\n";
    std::cout << "(якщо в консолі каша — це саме те, що й мало статися)\n\n";

    // ===== Частина 4: string_view приймає все і не копіює нічого =====
    auto describe = [](std::string_view word) {
        return std::string("слово \"") + std::string(word) + "\"";
    };

    std::string owned = "satya";
    const char* literal = "ahimsa";
    char buffer[] = "karma";

    std::cout << describe(owned)   << "\n";
    std::cout << describe(literal) << "\n";
    std::cout << describe(buffer)  << "   <- одна функція, три різні типи\n\n";

    // ===== Частина 5: пошук у рядку =====
    std::string line = "dharma — закон, обов'язок";
    size_t dash = line.find("—");
    if (dash != std::string::npos) {
        std::cout << "тире стоїть на байті " << dash << "\n";
        std::cout << "транслітерація: \"" << line.substr(0, dash - 1) << "\"\n";
        std::cout << "переклад:       \"" << line.substr(dash + 4) << "\"\n\n";
    }

    // ===== Частина 6: сирий літерал для шляху до словника =====
    const char* dictPath = R"(C:\Users\student\samskrta\data\dictionary.json)";
    std::cout << "шлях до словника: " << dictPath << "\n";
    std::cout << "без R\"(...)\" довелося б подвоювати кожен зворотний слеш\n";

    return 0;
}
```

धर्म           12        4
закон         10       5

байти "धर्म" у шістнадцятковому вигляді:
  E0 A4 A7 E0 A4 B0 E0 A5 8D E0 A4 AE

(якщо в консолі каша — це саме те, що й мало статися)

слово "satya"
слово "ahimsa"
слово "karma"   <- одна функція, три різні типи

транслітерація: "dharma"
переклад:       "закон, обов'язок"

Розберемо, що тут відбувається.

**`std::string::size()`** повертає кількість байтів, а не символів. Подивись на таблицю у виводі: `dharma` — 6 байтів і 6 code points, бо латиниця в UTF-8 займає рівно байт на літеру. `закон` — 10 байтів на 5 code points, бо кирилиця бере по два. А `धर्म` — 12 байтів на 4 code points, по три байти на кожен. Це джерело 90% багів у роботі з не-ASCII текстом: ти думаєш, що рядок має довжину 5, а `size()` каже 10.

**`(b & 0xC0) != 0x80`** у функції `countCodePoints` — те, як UTF-8 узагалі дозволяє себе рахувати. Кодування влаштоване так, що другий, третій і четвертий байти багатобайтової послідовності завжди починаються з бітів `10`. Маска `0xC0` — це `11000000`, вона лишає тільки два старші біти; якщо вони не дорівнюють `10`, значить, байт починає новий символ. Тому щоб порахувати code points, досить одного проходу без жодних таблиць і бібліотек. Це, до речі, і є головна практична перевага UTF-8 над іншими кодуваннями: за будь-яким байтом видно, він початок чи продовження, і рядок можна читати навіть із середини.

**Шістнадцятковий дамп** пояснює, звідки взялося число 4, яке більшість людей не очікує побачити у слові з трьох видимих знаків. `E0 A4 A7` — це U+0927, буква `ध` (dha). `E0 A4 B0` — U+0930, буква `र` (ra). `E0 A5 8D` — U+094D, і це не буква взагалі, а **вірама**: службовий знак, що каже «у попередньої приголосної немає власного голосного звуку». `E0 A4 AE` — U+092E, буква `म` (ma). Тобто `र` разом із вірамою не малюються окремо: вони зливаються з наступною буквою в один знак. Скільки саме знаків побачить людина, дивлячись на `धर्म`, — питання складніше, ніж здається, і відповідь на нього не вміє дати ані `size()`, ані наша функція. **Кількість байтів, кількість code points і кількість того, що людина назве символом, — це три різні числа**, і в деванагарі вони не збігаються ніколи. Рахувати третє з них ми навчимося в уроці 14, і там же стане ясно, чому це не робиться одним рядком.

**`substr(0, 4)`** ріже рядок по байтах і поняття не має, що десь усередині проходить межа символу. Ми взяли чотири байти: три перші склали повну `ध`, а четвертий — це початок наступної послідовності без її продовження. Результат — рядок, який не є коректним UTF-8, і при спробі показати його консоль малює символ-замінник. Правило звідси: **ніколи не ріж текст за байтовими позиціями**, якщо не впевнений, що там ASCII.

**`std::string_view` (C++17)** — одна з найважливіших речей у сучасному C++. Це «погляд на чужий рядок» — не копія, а тільки вказівник на початок і довжина. Уяви, що тобі показали абзац у чиємусь зошиті: ти бачиш текст, але забрати його додому не можеш. `string_view` — це точка зору на чужий рядок, без права власності. Головна перевага видно у виводі: одна функція `describe` прийняла `std::string`, `const char*` і масив `char[]` — без жодного перевантаження. Головна небезпека: якщо той, на кого дивився `string_view`, помре раніше — у тебе «висячий погляд», і це той самий висячий вказівник з уроку 5, тільки в новій обгортці.

**`std::string::npos`** — спеціальне значення «не знайдено». Класична ідіома — `if (pos != std::string::npos)`. У жодному разі не можна перевіряти `pos >= 0`, бо `size_t` — беззнаковий тип, і від'ємних значень у нього не буває в принципі. Ця перевірка завжди істинна, і компілятор із `/W4` про це попередить.

Зверни увагу на число 7 у рядку «тире стоїть на байті 7». Слово `dharma` — це шість байтів, потім пробіл, і тире починається саме з сьомого. Але сáме тире `—` займає три байти, тому щоб відрізати переклад, довелося написати `substr(dash + 4)`: три байти тире плюс пробіл. Ось так виглядає робота з текстом, коли рахуєш байти вручну, — і ось чому в уроці 7 ми радо перейдемо на `QString`.

**`R"(...)"`** — «сирий» (raw) рядковий літерал. Усередині не працюють екран-послідовності, тобто `\n` означає буквально «слеш і n», а не перенесення рядка. Ідеально для шляхів Windows і регулярних виразів, де інакше довелося б подвоїти кожен слеш. У нашому випадку це шлях до `data/dictionary.json` — файлу, який з'явиться в уроці 16 і в якому житиме весь словник.

**А тепер про `u8"..."`, якого у вправі навмисно немає.** Це UTF-8 літерал, і з ним сталася історія, варта уваги. У C++17 `u8"текст"` мав тип `const char[]` і спокійно клався в `std::string`. У C++20 його тип змінили на окремий `const char8_t[]`, який більше **не** перетворюється на `std::string` неявно. Тобто рядок `std::string s = u8"привіт";`, який роками був у підручниках, під C++20 просто не збирається:

```
error C2440: initializing: cannot convert from 'const char8_t [13]'
             to 'std::basic_string<char,...>'
```

Комітет зробив це навмисно: тепер компілятор явно розрізняє «просто байти» і «байти, у яких точно UTF-8», і мовчки плутати їх більше не дає. Лікується або явним приведенням через `reinterpret_cast`, або — простіше й чесніше — відмовою від префікса `u8` там, де результат однаково піде в `std::string`. Саме тому у вправі його немає: наші літерали і так у UTF-8, бо файл збережений у UTF-8, а компілятору про це сказано ключем `/utf-8` (на GCC і Clang — `-finput-charset=UTF-8 -fexec-charset=UTF-8`).

## Три пастки, які ловлять майже кожного

**Обрізаний символ** ми вже бачили у вправі, але варто підкреслити, наскільки це поширено. Ріже не лише `substr`: так само ламають текст будь-яке обмеження довжини поля в базі даних, обрізання довгого рядка трьома крапками в інтерфейсі, розбиття файлу на блоки фіксованого розміру при передачі мережею. Скрізь, де в коді є число байтів і текст не ASCII, рано чи пізно з'явиться половина символу. Лікування одне: різати за межами code points (а для показу користувачеві — за межами графем, і це вже урок 14), а не за байтами.

**Висячий вказівник на тимчасовий рядок.** `c_str()` віддає сирий вказівник на внутрішній буфер, і цей вказівник живе рівно стільки ж, скільки сам рядок:

```cpp
const char* danger = (std::string("тимчасовий") + " рядок").c_str();
std::cout << danger; // невизначена поведінка — рядок уже знищено
```

Вираз `std::string("тимчасовий") + " рядок"` створює тимчасовий об'єкт, який живе тільки до кінця цього рядка коду — та сама логіка висячого вказівника з уроку 5, тільки роль «функції, що завершилась» тут грає кінець виразу. Компілятор це не зупинить.

**Сортування не в тому сенсі, в якому думаєш.** Оператор `<` для `std::string` порівнює байти один за одним (лексикографічно) і нічого не знає про алфавітний порядок конкретної мови:

```cpp
std::vector<std::string> words = {"яблуко", "апельсин", "банан"};
std::sort(words.begin(), words.end());
```

Відсортує за числовими значеннями байтів UTF-8, а не за українським алфавітним порядком — для латиниці це випадково майже завжди «просто працює» (коди ASCII йдуть по порядку абетки), для кирилиці такого щастя немає. Правильне сортування за правилами конкретної мови називається **коляцією**, і голий `std::string` цього не вміє геть ніяк — знадобиться `std::locale` або, як ми побачимо в уроці 7, `QString`.

## Де це реально ламає системи

**Класична біль програміста**: відкрив файл, прочитав, в ньому замість «Привіт» — «Пр???в???». Що сталося? Ти читав UTF-8 (по 2 байти на літеру) і відкривав як Windows-1251 (по 1 байту). Кожні два байти інтерпретувалися як два окремих символи, і більшість із них — невизначені в 1251. Класика, через яку проходить кожен. Ліки: `setlocale(LC_ALL, "uk_UA.UTF-8")` або `std::locale("")` на початку програми. Але навіть це не гарантія — в Windows консоль живе у своєму кодуванні (`chcp 866` за замовчуванням у російській Windows), і треба окремо перемикати `chcp 65001` для UTF-8.

**ICU (International Components for Unicode)** — бібліотека, яка вміє все, що стосується Unicode: нормалізація, перетворення кодувань, робота з календарями, валютами, іменами. Без неї серйозний проект із інтернаціоналізацією — як кухня без ножів. Qt має свою вбудовану систему (`QString`, `QTextCodec`), стандартна бібліотека C++ — обмежену.

**JSON-парсери** в реальному житті завжди працюють із `std::string_view` для ключів і значень — це дозволяє парсити величезні файли без копіювання. Коли бачиш в API парсера типу `nlohmann::json`, подивись у її вихідний код — там всюди `string_view`. Це золотий стандарт сучасного C++.

**Аналогія з перекладом**: уяви, що ти в посольстві, і тобі потрібно передати текст українською індійському дипломатові. Ти даєш йому аркуш паперу (UTF-8) — він має словник (таблиця Unicode) і розуміє, що це. А тепер уяви, що ти дав йому фотографію аркуша (UTF-16, два байти на літеру) — словник той самий, але методика інша. А якщо ти дав йому подвійну фотографію (UTF-32, чотири байти) — словник той самий, але папір витрачено вчетверо. UTF — це методика кодування, Unicode — це словник. Плутати їх — все одно що плутати мову з алфавітом. Алфавіт — кирилиця, мова — українська. Кодування — UTF-8, алфавіт — Unicode code points.

## Куди йти, якщо std::string замало

**Замість `std::string`** для тексту з Unicode:

- **Qt: `QString`** — найзручніший варіант для нашого проекту. Внутрішньо UTF-16, але ти цього не бачиш. Є методи `arg()` для форматування, `split()`, `mid()` — справжня робота з текстом, а не з байтами.
- **ICU: `UnicodeString`** — потужно, важко, повільно компілюється. Для проектів, де Qt — занадто багато, а `std::string` — замало.
- **Boost.Nowide** — для тих, хто хоче std-стиль, але з нормальною підтримкою UTF-8 на Windows.

**Замість `std::string_view` як параметр** — іноді варто брати `const std::string&`. Так, це копія при кожному виклику, але якщо функція зберігає рядок у себе — `string_view` не підходить (його базова пам'ять може померти). Правило: `string_view` — для тих, хто просто «подивитися і відпустити», `const std::string&` — для тих, хто «подивитися і зберегти посилання», `std::string` — для тих, хто «забрати додому».

**Замість `+` для конкатенації** — у новому C++20 з'явився `std::format` (як у Python):

```cpp
// Старий стиль
std::string msg = "Користувач " + name + " вивчив " + std::to_string(count) + " слів";

// Новий стиль (C++20)
std::string msg = std::format("Користувач {} вивчив {} слів", name, count);
```

Швидше, читабельніше, безпечніше. Якщо компілятор не підтримує — бібліотека `{fmt}` дає те саме зараз.

2. Чим небезпечний `string_view`, якщо базовий `std::string` помер раніше? Напиши приклад, де це станеться.
3. Напиши функцію `bool containsWord(const std::string& text, std::string_view word)`, яка перевіряє, чи є `word` у `text`. Використай `find`.
4. Поясни різницю між `u8"текст"`, `u"текст"`, `U"текст"` і `L"текст"`. Що змінилося в C++20 для `u8`?
