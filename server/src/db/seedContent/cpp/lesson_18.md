# Урок 18. SIMD: одна інструкція, багато даних

## Пролог: коли одного ядра мало

Уяви, що тобі треба перевести 10 000 слів. Звичайний цикл — одне слово за раз. Процесор із частотою 3 ГГц — близько 3 мільярди операцій за секунду. На одне слово — десятки операцій, плюс доступ до пам'яті. Виходить десь 100 000 слів за секунду. Непогано, але не блискавично.

Тепер уяви, що процесор уміє робити **8 операцій за раз** — на спеціальних 256-бітних регістрах, які вміщають 8 чисел по 32 біти кожне. Тобто замість 8 інструкцій (`a[0]+b[0]`, `a[1]+b[1]`, ..., `a[7]+b[7]`) — одна. І робить вона це за один такт. Це і є SIMD — Single Instruction, Multiple Data. Одна інструкція, багато даних. Процесор перетворюється з «одного працівника з лопатою» на «бригаду з восьми працівників, які копають паралельно».

У цьому уроці ми подивимося, як це працює на практиці. Без ручного асемблера (цьому присвятимо наступний урок), через інтринсики — спеціальні функції, які виглядають як C++, але компілюються в конкретні SIMD-інструкції процесора.

## Код уроку

Вправа — `exercises/ex18_simd.cpp`, і рахує вона цілком прикладну річ: скільки в словнику складних слів і яка середня складність. Це те, що показує екран статистики. На десяти словах питання безглузде, на десяти мільйонах — уже ні.

```cmake
add_executable(ex18_simd  exercises/ex18_simd.cpp)
if(MSVC)
    target_compile_options(ex18_simd PRIVATE /arch:AVX2)
else()
    target_compile_options(ex18_simd PRIVATE -mavx2)
endif()
```

Перше, з чим доведеться змиритися: **SIMD не вміє працювати з нашим `std::vector<Word>`**. Рівні складності лежать не поспіль, а через кожні `sizeof(Word)` байтів, розділені трьома рядками. Щоб віддати їх процесору пачкою, спершу треба зібрати їх у власний масив. Це називають переходом від «масиву структур» (AoS) до «структури масивів» (SoA), і саме на цьому спотикається більшість спроб прискорити код через SIMD.

```cpp
// exercises/ex18_simd.cpp — серцевина; повний файл лежить у проєкті

#include <immintrin.h>          // AVX2: працює і на MSVC, і на GCC/Clang
#include "../src/domain/Word.h"

// ===== Чесно поелементний підрахунок =====
// Прагма забороняє компілятору самому векторизувати цей цикл —
// тільки так можна побачити, скільки коштує обробка по одному числу.
int countHardPlain(const std::vector<int>& levels, int threshold) {
    int count = 0;
    const int* p = levels.data();
    const size_t n = levels.size();
#ifdef _MSC_VER
    #pragma loop(no_vector)
#endif
    for (size_t i = 0; i < n; ++i) {
        if (p[i] >= threshold) ++count;
    }
    return count;
}

// ===== Той самий код, але компілятору дозволено все =====
int countHardScalar(const std::vector<int>& levels, int threshold) {
    int count = 0;
    for (int lvl : levels) {
        if (lvl >= threshold) ++count;
    }
    return count;
}

// ===== І він же руками на AVX2: вісім рівнів за одну інструкцію =====
int countHardAVX2(const std::vector<int>& levels, int threshold) {
    const int* p = levels.data();
    const size_t n = levels.size();

    // Вісім копій числа (threshold - 1): порівнюємо через "строго більше"
    __m256i vLimit = _mm256_set1_epi32(threshold - 1);
    __m256i vCount = _mm256_setzero_si256();

    size_t i = 0;
    for (; i + 8 <= n; i += 8) {
        __m256i vLevels = _mm256_loadu_si256(reinterpret_cast<const __m256i*>(p + i));
        // Маска: там, де рівень більший за limit, усі біти = 1, тобто число -1
        __m256i vMask = _mm256_cmpgt_epi32(vLevels, vLimit);
        // Віднімаємо -1 = додаємо 1. Вісім лічильників ростуть паралельно.
        vCount = _mm256_sub_epi32(vCount, vMask);
    }

    // Складаємо вісім часткових лічильників в один
    alignas(32) int parts[8];
    _mm256_store_si256(reinterpret_cast<__m256i*>(parts), vCount);
    int count = 0;
    for (int k = 0; k < 8; ++k) count += parts[k];

    // Хвіст: те, що не влізло у вісімку
    for (; i < n; ++i) {
        if (p[i] >= threshold) ++count;
    }
    return count;
}
```

Вивід (MSVC, `/O2 /arch:AVX2`, 10 мільйонів слів, кожен замір усереднено по 20 запусках):

```
Словник: 10000000 слів

sizeof(Word) = 120 байтів, з них рівень займає 4
тобто в масиві структур корисних для нас даних — 3.3%

складних слів (рівень >= 4):
  скалярно: 4000000
  AVX2:     4000000   <- збігається
сума рівнів:
  скалярно: 30000000
  AVX2:     30000000   <- збігається
середня складність: 3.000

підрахунок складних:
  по одному (векторизацію вимкнено): 6.15 мс
  звичайний цикл, /O2:               2.52 мс   2.45x
  руками на AVX2:                    2.35 мс   2.61x
сума рівнів:
  скалярно: 2.53 мс
  AVX2:     2.29 мс   прискорення 1.11x
```

Ці три числа варто розглянути уважно, бо вони суперечать усьому, що зазвичай пишуть про SIMD.

**Перше: 3.3%.** У масиві з десяти мільйонів `Word` рівні складності займають 40 мегабайтів, а сам масив — 1.2 гігабайта. Читаючи структури підряд, процесор тягне з пам'яті в тридцять разів більше даних, ніж йому потрібно, і викидає 97% прочитаного. Ось чому перед будь-якою серйозною оптимізацією обчислень першим кроком іде **перекладання даних**, а не переписування циклів.

**Друге: 2.45x без жодного рядка SIMD-коду.** Різниця між першим і другим рядком замірів — це те, що зробив компілятор сам. Той самий цикл `if (lvl >= threshold) ++count;`, просто без заборонної прагми. MSVC із `/O2 /arch:AVX2` розпізнав його й підставив ті самі інструкції, які я нижче писав руками. Автовекторизація вміє це вже років п'ятнадцять, і працює вона для простих циклів без залежностей між ітераціями.

**Третє, найнеприємніше: руками вийшло 2.61x проти 2.45x.** Тобто весь мій ретельно виписаний AVX2-код дав додаткові **сім відсотків** до того, що компілятор зробив безкоштовно. На сумі рівнів різниця ще менша — 11% над скалярним варіантом.

Чому не вісім разів, як обіцяє арифметика «вісім чисел за інструкцію»? Тому що вузьке місце тут не в обчисленнях. Сорок мегабайтів не вміщуються в кеш процесора, і цикл упирається не в швидкість додавання, а в **пропускну здатність пам'яті**: процесор просто не встигає отримувати дані з такою швидкістю, з якою міг би їх обробляти. Скільки чисел ти складаєш за одну інструкцію — вісім чи одне — не має значення, якщо обидва варіанти чекають на пам'ять.

Практичний висновок, який суперечить репутації SIMD: **писати інтринсики вручну має сенс тільки тоді, коли ти спершу подивився, що зробив компілятор, і переконався, що він не впорався**. Причини, з яких він не впорається, зазвичай такі: у циклі є залежність між ітераціями, є розгалуження зі складною умовою, є виклик функції, або потрібна інструкція без скалярного аналога (як `PCMPISTRI` для пошуку підрядка). У решті випадків достатньо ввімкнути `/O2` і не заважати.

Розберемо, що тут відбувається.

**`__m256i`** — тип із 256-бітного регістра. Це не звичайна змінна — це «тримання» в SIMD-регістрі процесора. Ти не можеш звернутися до окремих елементів напряму (тільки через спеціальні функції), не можеш зробити `std::cout << va;`. Тільки завантажити з пам'яті, зробити операцію, зберегти назад.

**`_mm256_loadu_si256`** — «завантаж 8 int32 з пам'яті в SIMD-регістр». `u` означає «unaligned»: адреса не обов'язково має бути кратна 32 байтам. Є й вимоглива версія `_mm256_load_si256`, яка на невирівняній адресі аварійно завершує програму; на сучасних процесорах різниці в швидкості між ними практично немає, тому в новому коді беруть `loadu` і не морочаться.

**`_mm256_set1_epi32(x)`** — «зроби регістр із восьми однакових чисел `x`». Так ми готуємо межу для порівняння: одне число розмножується на всі вісім доріжок, щоб порівнювати кожен рівень одразу з нею.

**`_mm256_cmpgt_epi32(a, b)`** — порівняння восьми пар одразу. Результат не `true`/`false`, а маска: у тих доріжках, де `a > b`, стоять усі одиниці, тобто число `-1`; де ні — усі нулі. Саме тому далі йде **`_mm256_sub_epi32(vCount, vMask)`**: відняти `-1` означає додати одиницю. Вісім лічильників ростуть паралельно, і жодного розгалуження в циклі немає — це принципово, бо непередбачуване розгалуження коштує процесору десятків тактів на кожній помилці передбачення.

**`alignas(32) int parts[8]`** і **`_mm256_store_si256`** — вивантаження регістра назад у звичайний масив. Тут уже потрібна саме вирівняна версія `store`, тому масив оголошений з `alignas(32)`: компілятор гарантує, що його адреса кратна 32 байтам. Далі вісім часткових лічильників складаються звичайним циклом — цю операцію називають **горизонтальним додаванням**, і вона в SIMD завжди повільна, тому її роблять один раз у кінці, а не всередині циклу.

**`epi32`** у назвах — це «packed 32-bit signed integers». За тим самим принципом влаштована вся система імен: `_mm256_` — ширина 256 біт, далі дія, далі тип елементів. `_mm256_add_epi16` складав би шістнадцять 16-бітних чисел, `_mm256_add_ps` — вісім `float`. Назви виглядають страхітливо рівно доти, доки не помічаєш цю схему.

**Хвіст (tail)** — елементи, що не влізли в 8. Якщо `N = 10 000 001`, ми обробимо 10 000 000 елементів через SIMD (1 250 000 ітерацій по 8), і 1 елемент залишиться — його обробляємо скалярно. Без хвоста ми б проігнорували останній елемент або вийшли за межі масиву.

**`<immintrin.h>`** — заголовок з інтринсиками. Раніше доводилося писати `#ifdef _MSC_VER` і підключати `<intrin.h>` на MSVC, але вже багато років `<immintrin.h>` працює однаково на MSVC, GCC і Clang, тож розгалуження більше не потрібне.

**`_mm256_loadu_si256(reinterpret_cast<...>)`** — потрібно, тому що компілятор бачить `int*` (8 байт), а ми хочемо передати `__m256i*` (32 байти). `reinterpret_cast` каже «не перевіряй типи, я знаю, що роблю». Це класичне місце, де компілятор не допомагає, а ти сам відповідаєш за правильність.

## Пастка, про яку легко забути: не кожен процесор так уміє

Код вище скомпілюється й запрацює на твоїй машині — але AVX2 доступний не на кожному процесорі, на якому колись запуститься готовий SAMSKRTA. Запустити `_mm256_add_epi32` на старому процесорі без підтримки AVX2 — не помилка компіляції, а аварійне завершення просто в момент виконання (`illegal instruction`). Тому перед реальним використанням SIMD у проєкті підтримку перевіряють у рантаймі:

```cpp
int cpuInfo[4];
__cpuidex(cpuInfo, 7, 0);
bool hasAVX2 = (cpuInfo[1] & (1 << 5)) != 0;
```

і, якщо підтримки немає, відкочуються на менш продуктивний, але гарантовано доступний варіант — старіший SSE2 або звичайний скалярний цикл. І ще важливіше за саму перевірку: перш ніж вбудовувати SIMD-версію в проєкт, зміряй обидві версії на реальних даних свого словника, а не повір на слово. На маленькому словнику різниця часто тоне в похибці заміру — SIMD там чиста зайва складність, а не покращення. Виправданим він стає рівно тоді, коли зростання даних робить різницю вимірюваною, і не раніше.

## Де це реально використовується

**Лінійна алгебра** — головний споживач SIMD. BLAS (Basic Linear Algebra Subprograms) — стандартна бібліотека лінійної алгебри — використовує SIMD на повну. Intel MKL, OpenBLAS, ATLAS — усі вони в ядрі мають SIMD-інструкції. Множення матриць, розкладання Холецького, SVD — все це в рази швидше з SIMD.

**Кодеки відео та аудіо** — x264, x265, FFmpeg, libvpx активно використовують SIMD для кодування/декодування. Перетворення Фур'є, дискретне косинусне перетворення, фільтри — усе це «природно паралельні» операції, які ідеально лягають на SIMD. Без SIMD — відео 4K не кодувалося б у реальному часі.

**Обробка зображень** — OpenCV, ImageMagick, бібліотеки для обробки RAW-файлів — усі використовують SIMD. Розмиття, збільшення різкості, зміна кольорів — все це операції «застосуй функцію до кожного пікселя», і SIMD тут ідеально.

**Криптографія** — AES-NI (Intel), SHA Extensions — це SIMD-інструкції спеціально для шифрування. OpenSSL використовує їх, щоб HTTPS-трафік оброблявся швидко.

**Google TPU, NVIDIA CUDA, Apple Neural Engine** — це вже «SIMD на стероїдах». Тисячі ядер, кожне робить свою SIMD-операцію. Машинне навчання без них було б у тисячі разів повільнішим.

**Аналогія з пральною машиною**: уяви, що тобі треба випрати 16 сорочок. Звичайна пранка — одна за раз, 16 циклів. SIMD — це пральна машина з 8 барабанами: завантажив 8 сорочок, запустив один цикл, вийняв 8 чистих. За 2 цикли — 16 сорочок готові. В 4 рази швидше. У реальності ще швидше, бо й воду грієш один раз, і пральний засіб додаєш один раз. SIMD — це та сама «восьмибарабанна пралка» для процесора.

## Куди це веде далі

**Замість ручних інтринсиків** — компілятор часто робить це сам. Увімкни `-O3` (або `/O2` для MSVC) і подивись на асемблерний вивід — компілятор сам використовує SIMD, коли може. Для простих циклів ти можеш навіть не помітити різниці між ручним SIMD і тим, що зробив компілятор. Але для складних обчислень — ручний SIMD швидше.

**Замість низькорівневих інтринсиків** — бібліотеки вищого рівня:
- **Eigen** — лінійна алгебра з автоматичним SIMD
- **OpenCV** — обробка зображень
- **VCL** (Vector Class Library) — С++ обгортка над SIMD
- **xsimd** — ще одна сучасна обгортка

**Замість AVX2** — сучасніші розширення: AVX-512 (Intel), SVE/SVE2 (ARM). Дають ще ширші регістри (512 біт замість 256), більше інструкцій, складніші. Не скрізь доступні, але якщо компілюєш під конкретне залізо — варто.

**Замість SIMD** — GPU. Якщо задача «природно паралельна» (одна операція над мільйонами даних), GPU дасть сотні й тисячі ядер. CUDA (NVIDIA), OpenCL (крос-платформний), SYCL (наступник OpenCL). Для машинного навчання, обробки зображень, фізичних симуляцій — GPU зазвичай швидше.

## Питання для самоперевірки

1. Збери з `-O3` (або `/O2`). Запусти. Запиши результати.
2. Зміни `int` на `float`. Чи змінилася швидкість? Чому?
3. Спробуй `long long` (64-біт). Скільки елементів тепер влазить в один SIMD-регістр? Як зміниться швидкість?
4. Додай в AVX2-версію обробку хвоста. Перевір, що результат збігається зі скалярною версією для непарного розміру масиву.
5. Помнож замість додавання (`_mm256_mullo_epi32`). Виміряй швидкість. Чи таке саме прискорення?

**На наступному уроці**: асемблер. Один раз, повністю, без страху. Ми вже бачили, як компілятор перетворює наш код на машинні інструкції — тепер напишемо їх самі, на x86-64. Це не магія, це просто текст.
