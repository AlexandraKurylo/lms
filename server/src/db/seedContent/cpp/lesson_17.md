# Урок 17. Багатопотоковість: від одного стрибка до квесту

## Вступ: один потік — це нормально (поки не ні)

Поки що всі наші програми мали один потік: одна послідовність інструкцій, яка виконується від початку до кінця. І все працює. Але уяви, що наш SAMSKRTA має завантажити словник із 10 000 слів із бази даних, перевірити оновлення через інтернет, і при цьому не зависнути, поки користувач натискає кнопки. В одному потоці — зависне. У двох — одне робиться, інше чекає, головне вікно реагує.

Сьогодні ми розберемося в основах багатопотоковості: як створити потік, як синхронізувати доступ до спільних даних, що таке гонка даних і як її уникнути. Це одна з найскладніших тем у програмуванні — і одна з найважливіших.

## Код уроку

Вправа — `exercises/ex17_threads.cpp`. Перші три частини працюють зі звичайним лічильником переглянутих слів, а четверта перевіряє те, повз що ми пройшли в уроці 9: там у `Database::addWord` стояв `std::lock_guard`, і я попросив просто запам'ятати шаблон. Тепер перевіримо, чи він справді щось робить.

```cmake
add_executable(ex17_threads  exercises/ex17_threads.cpp)
find_package(Threads REQUIRED)
target_link_libraries(ex17_threads PRIVATE Threads::Threads)
```

Ці два додаткові рядки CMake потрібні тільки на Linux і macOS, де потоки живуть в окремій бібліотеці `pthread`. На Windows MSVC має все всередині, і `find_package(Threads)` там просто нічого не робить. Писати їх варто завжди — так проєкт збереться скрізь.

```cpp
// exercises/ex17_threads.cpp
// Гонка даних, м'ютекс, atomic — і перевірка, що наш Database справді безпечний.

#include <iostream>
#include <thread>
#include <mutex>
#include <atomic>
#include <vector>
#include <set>
#include "../src/data/Database.h"

// ===== Лічильник переглянутих слів: без жодного захисту =====
int unsafeReviewed = 0;

void unsafeCount(int times) {
    for (int i = 0; i < times; ++i) {
        ++unsafeReviewed;   // читання, додавання, запис — три окремі дії
    }
}

// ===== Той самий лічильник під м'ютексом =====
std::mutex reviewedMutex;
int safeReviewed = 0;

void safeCount(int times) {
    for (int i = 0; i < times; ++i) {
        std::lock_guard<std::mutex> lock(reviewedMutex);
        ++safeReviewed;
    }
}

// ===== І він же як atomic =====
std::atomic<int> atomicReviewed{0};

void atomicCount(int times) {
    for (int i = 0; i < times; ++i) {
        ++atomicReviewed;   // одна неподільна інструкція процесора
    }
}

// ===== Потік, що наповнює справжню базу =====
void importerThread(int threadNo, int wordsPerThread) {
    auto& db = Database::instance();
    for (int i = 0; i < wordsPerThread; ++i) {
        db.addWord(Word("धर्म",
                        "w" + std::to_string(threadNo) + "_" + std::to_string(i),
                        "переклад", (i % 5) + 1));
    }
}

template <typename Func>
void runInThreads(int count, Func f) {
    std::vector<std::thread> threads;
    threads.reserve(static_cast<size_t>(count));
    for (int i = 0; i < count; ++i) threads.emplace_back(f, i);
    for (auto& t : threads) t.join();
}

int main() {
    const int THREADS = 4;
    const int PER_THREAD = 100000;

    std::cout << "=== Частина 1: гонка даних ===\n";
    runInThreads(THREADS, [&](int) { unsafeCount(PER_THREAD); });
    std::cout << "  очікувано: " << THREADS * PER_THREAD << "\n";
    std::cout << "  отримано:  " << unsafeReviewed << "\n";
    std::cout << "  втрачено:  " << (THREADS * PER_THREAD - unsafeReviewed)
              << "  <- це і є гонка\n\n";

    std::cout << "=== Частина 2: той самий лічильник під м'ютексом ===\n";
    runInThreads(THREADS, [&](int) { safeCount(PER_THREAD); });
    std::cout << "  отримано:  " << safeReviewed << "\n\n";

    std::cout << "=== Частина 3: він же як std::atomic ===\n";
    runInThreads(THREADS, [&](int) { atomicCount(PER_THREAD); });
    std::cout << "  отримано:  " << atomicReviewed.load() << "\n\n";

    std::cout << "=== Частина 4: чотири потоки пишуть у наш Database ===\n";
    const int WORDS_PER_THREAD = 250;
    runInThreads(THREADS, [&](int no) { importerThread(no, WORDS_PER_THREAD); });

    auto& db = Database::instance();
    std::cout << "  очікувано слів: " << THREADS * WORDS_PER_THREAD << "\n";
    std::cout << "  у базі:         " << db.count() << "\n";

    // Найважливіша перевірка: чи не видала база двом словам однаковий id
    std::set<int> ids;
    int duplicates = 0;
    for (const auto& w : db.allWords()) {
        if (!ids.insert(w.id).second) ++duplicates;
    }
    std::cout << "  унікальних id:  " << ids.size() << "\n";
    std::cout << "  дублікатів id:  " << duplicates << "\n";

    return 0;
}
```

Вивід у **налагоджувальній** збірці (`/Od`, тобто без оптимізації):

```
=== Частина 1: гонка даних ===
  очікувано: 400000
  отримано:  179110
  втрачено:  220890  <- це і є гонка

=== Частина 2: той самий лічильник під м'ютексом ===
  отримано:  400000

=== Частина 3: він же як std::atomic ===
  отримано:  400000

=== Частина 4: чотири потоки пишуть у наш Database ===
[Database] створено (один раз)
  очікувано слів: 1000
  у базі:         1000
  унікальних id:  1000
  дублікатів id:  0
[Database] знищено (один раз, у кінці програми)
```

**Більше половини інкрементів зникло безслідно.** Чотири потоки виконали разом 400 000 операцій `++`, а лічильник показує 179 110. Другий запуск дав 139 498 — число різне щоразу, бо залежить від того, як саме планувальник ОС переплітав потоки в ту конкретну мілісекунду.

Причина в тому, що `++unsafeReviewed` — це не одна дія, а три: прочитати значення з пам'яті в регістр, додати одиницю, записати назад. Два потоки читають однакове число, обидва додають одиницю, обидва записують — і замість двох інкрементів виходить один. Чим більше потоків, тим частіше це трапляється.

А тепер найважливіше в усьому уроці. Ось той самий код, зібраний з оптимізацією (`/O2`):

```
=== Частина 1: гонка даних ===
  очікувано: 400000
  отримано:  400000
  втрачено:  0  <- це і є гонка
```

**Гонка зникла.** Не виправилася — саме зникла з поля зору. Оптимізатор побачив цикл, який сто тисяч разів додає одиницю до однієї змінної, і згорнув його в одну операцію `unsafeReviewed += 100000`. Вікно, у яке міг втрутитися інший потік, скоротилося з ста тисяч моментів до одного, і ймовірність зіткнення впала майже до нуля.

Код лишився так само неправильним. Просто тепер він поводиться правильно — на цьому компіляторі, з цими прапорцями, на цій машині, сьогодні. Змінити версію компілятора, додати рядок логування всередину циклу, запустити на процесорі з іншою кількістю ядер — і помилка повернеться, у продакшні, через півроку після релізу. **Саме тому гонки даних не шукають запуском.** Для них є інструмент: `-fsanitize=thread` на GCC і Clang (ThreadSanitizer), який знаходить гонку навіть тоді, коли вона жодного разу не проявилася при виконанні.

І окремо — частина 4. Тисяча слів, доданих з чотирьох потоків одночасно, дала рівно тисячу записів із тисячею різних `id`. Жодного дубліката. Той `std::lock_guard<std::mutex> lock(m_mutex);`, який ми написали в уроці 9 і відклали на потім, — саме він і не дав рядку `word.id = ++m_nextId;` перетворитися на таку саму гонку, як у частині 1. Ті ж три дії — прочитати, додати, записати — але під замком.

## Дедлок: коли всі чекають і ніхто не рухається

Гонка — не єдина біда багатопотоковості. Є друга, симетрична: замість того щоб зіткнутися, потоки можуть завмерти назавжди. Ось як це виглядає в коді:

```cpp
std::mutex mutexA;
std::mutex mutexB;

void threadA() {
    std::lock_guard<std::mutex> lockA(mutexA);
    std::this_thread::sleep_for(std::chrono::milliseconds(10));
    std::lock_guard<std::mutex> lockB(mutexB);   // чекає на B
    std::cout << "  [A] отримав обидва м'ютекси\n";
}

void threadB() {
    std::lock_guard<std::mutex> lockB(mutexB);
    std::this_thread::sleep_for(std::chrono::milliseconds(10));
    std::lock_guard<std::mutex> lockA(mutexA);   // чекає на A — ДЕДЛОК
    std::cout << "  [B] отримав обидва м'ютекси\n";
}
```

Запускати це у вправі я не став навмисно: програма зависне назавжди, і її доведеться вбивати диспетчером задач. Але якщо хочеш побачити на власні очі — додай два рядки в `main` і будь готовий натиснути Ctrl+C:

```cpp
std::thread ta(threadA);
std::thread tb(threadB);
ta.join();
tb.join();
```

Логіка збою проста. Потік A замкнув `mutexA` і чекає на `mutexB`. Потік B замкнув `mutexB` і чекає на `mutexA`. Жоден не відпустить своє, поки не отримає чуже, — і так до кінця світу. Пауза `sleep_for` тут потрібна лише для того, щоб дедлок стався гарантовано: без неї один потік часто встигає взяти обидва замки раніше, ніж другий почне.

Лікування є, і воно просте. **Або** завжди бери м'ютекси в одному й тому самому порядку в усій програмі (спочатку `mutexA`, потім `mutexB`, ніколи навпаки). **Або** бери їх разом однією операцією — для цього з C++17 є `std::scoped_lock`, який замикає скільки завгодно м'ютексів атомарно й без ризику дедлоку:

```cpp
void threadA() {
    std::scoped_lock lock(mutexA, mutexB);   // обидва разом або жодного
    std::cout << "  [A] отримав обидва м'ютекси\n";
}
```

Один рядок замість двох, і проблема зникає в принципі. У Qt те саме роблять через `QMutexLocker`, а до C++17 писали `std::lock(mutexA, mutexB)` з двома `lock_guard` і прапорцем `std::adopt_lock` — некрасиво, але працювало.

Розберемо, що тут відбувається.

**`std::thread`** — стандартний спосіб створити потік у C++11. Приймає функцію (або лямбду, або callable-об'єкт) і аргументи. Потік починає виконуватися негайно, в конструкторі. Ти можеш дочекатися його завершення через `join()` або від'єднати через `detach()` (в останньому випадку потік працює «сам по собі»). Забув `join()` або `detach()` до знищення об'єкта `thread` — `std::terminate` і аварійне завершення.

**`std::mutex`** — примітив синхронізації. Уяви замок: один потік замикає, інший чекає, перший відмикає. `lock()` блокує, `unlock()` відмикає. `std::lock_guard` — RAII-обгортка: заблокував у конструкторі, відблокував у деструкторі. Використовуй завжди `lock_guard` замість ручного `lock/unlock`, бо `lock_guard` гарантує відблокування навіть при винятку. Це одна з тих речей, які після першого використання здаються настільки очевидними, що незрозуміло, як без них жили.

**Гонка даних (data race)** — коли два потоки звертаються до однієї змінної одночасно, і хоча б один із них пише. Результат непередбачуваний: від «працює випадково» до «працює завжди, крім того дня, коли ти презентуєш проект босові». У нашому прикладі `unsafeReviewed` рідко дає правильний результат, тому що `++` — це не одна операція, а три (прочитати, додати 1, записати). Між ними інший потік може прочитати те саме значення і додати своє — обидва записують старе значення, одне з додавань губиться. Це називається «lost update».

**`std::atomic<T>`** — тип, операції над яким атомарні на рівні процесора. `++atomicReviewed` — це одна операція, її не можна «перервати» посередині. Швидше за `mutex`, бо не потребує переключення контексту, але підходить тільки для простих операцій (лічильники, прапорці, вказівники). Для складних структур — тільки `mutex`.

**Дедлок (deadlock)** — взаємне блокування. Потік A чекає на ресурс, який тримає потік B. Потік B чекає на ресурс, який тримає потік A. Обидва чекають вічно. У нашому прикладі — класична ситуація: A брав A, потім чекає B; B брав B, потім чекає A. Рішення: завжди брати м'ютекси в однаковому порядку, або використовувати `std::lock()`, який атомарно б'є кілька м'ютексів. У Qt є `QMutexLocker` (теж RAII, як `lock_guard`).

**`std::this_thread::sleep_for`** — примусова пауза в потоці. Використовується тут, щоб дедлок встиг статися (без паузи один потік може встигнути все зробити до того, як інший почне). У реальному коді — рідко, тільки в тестах, де треба відтворити race condition.

**`join()`** — чекати завершення потоку. Без `join()` деструктор `std::thread` викликає `std::terminate`. Це навмисне: програма повинна явно вирішити, чи хоче вона дочекатися потоку. «Забув join» — помилка, яку компілятор ловить.

## Два правила Qt, які не можна порушувати

Все, що ми писали з уроку 7, жило в одному-єдиному потоці — тому самому, де крутиться цикл подій Qt. Щойно в проєкті з'являється другий потік, до звичайних гонок і дедлоків додаються два специфічно Qt-шних правила.

**Перше: віджети можна створювати й міняти тільки з головного потоку.** Фоновий потік, що завершив важку роботу, не може напряму дотягнутися до `QLabel` чи `QProgressBar` і оновити текст. Замість цього він надсилає сигнал, а Qt сам ставить виклик підключеного слота в чергу подій головного потоку — той самий механізм сигналів і слотів з уроку 7, тепер уже не заради зручності, а як інструмент безпеки.

**Друге: `QSqlDatabase`, відкрита в одному потоці, не може використовуватись із іншого.** Це не порада, а архітектурне обмеження драйвера. Якщо словник вантажиться у фоновому потоці — кожен потік мусить відкрити своє власне з'єднання з тим самим файлом бази (SQLite це підтримує), а не ділити одне на всіх.

Обидва правила Qt не порушить одразу — покарає падінням через місяць, у найнепередбачуваніший момент, без жодної підказки, звідки воно взялося.

## Де це реально болить

**Chromium** має тисячі потоків: рендеринг, мережа, введення-виведення, обробка зображень, JavaScript. Кожна вкладка — це окремий процес із своїми потоками. Синхронізація — через атоміки, м'ютекси, lock-free структури даних. Помилки синхронізації — це 30% усіх серйозних багів у Chromium.

**PostgreSQL** обробляє кожне з'єднання в окремому потоці. М'ютекси захищають спільні структури (кеш запитів, логи). У них навіть є спеціальний режим — «lock-free mode» для деяких операцій, де м'ютекси занадто повільні.

**Ігрові рушії** — окремий потік на рендеринг, окремий на фізику, окремий на аудіо, окремий на введення. Синхронізація — через події та черги повідомлень (наприклад, рух гравця → черга → фізика → черга → рендер). У Unreal Engine є ціла система FRunnable для управління потоками, у Qt — `QThread`.

**Класична помилка 2018 року в Ethereum** — race condition у смарт-контракті, через який можна було витратити чужі гроші. Контракт `Fomo3D` дозволяв «виграти» двом гравцям одночасно через гонку в обробці транзакцій. Це призвело до втрат у мільйони доларів. Багатопотоковість + фінанси = максимальна увага.

**Аналогія з кухнею ресторану**: один потік — це кухар, який спочатку нарізає овочі, потім смажить м'ясо, потім варить суп. Все послідовно. Багатопотоковість — це три кухарі, кожен робить свою страву. Але вони користуються спільною плитою, спільними ножами. Якщо не домовитися — один візьме ніж, поки інший ріже, і буде кров. М'ютекси — це правило «хто взяв ніж, той ріже, інший чекає». Атоміки — це «у ножа тільки одне лезо, і воно або вільне, або зайняте». Дедлок — два кухарі тримаються за один ніж і не відпускають, чекаючи, поки інший відпустить. Ресторан закривається.

## Застосовуємо до SAMSKRTA: завантаження словника у фоні

Поки в `Database` (уроки 9, 15, 16) кілька слів, завантаження з диска в конструкторі непомітне. Але коли `WordRepository` вантажитиме тисячі слів, робити це прямо в конструкторі `Database`, який викликається з головного потоку при старті вікна з уроку 7, — заморозити інтерфейс на весь час читання файлу. Ось як виглядає фонове завантаження з дотриманням обох правил Qt-потокобезпеки з початку уроку:

```cpp
// у main.cpp, після створення window, але до window.show()
std::thread loader([&window]() {
    auto& db = Database::instance();       // сам синглтон уже прочитав файл у ctor
    QMetaObject::invokeMethod(&window, [&window, count = db.count()]() {
        // це лямбда виконається в головному потоці — тут уже можна чіпати віджети
        window.setWindowTitle(QString("SAMSKRTA — %1 слів").arg(count));
    });
});
loader.detach();  // не чекаємо — вікно вже показане й відповідає
```

`QMetaObject::invokeMethod` з лямбдою — ще один спосіб (крім сигналів/слотів) поставити код у чергу подій головного потоку: сам фоновий потік ніколи не торкається `window` напряму, тільки просить головний потік зробити це замість нього. Саме це і є практичне застосування правила «віджети — тільки з головного потоку» з нашого власного проєкту, а не абстрактний приклад.

## Куди це веде далі

**Замість `std::thread` + `std::mutex`** у Qt-проектах — `QThread` + `QMutex`:

```cpp
QThread thread([&]() {
    // фонова робота
});
thread.start();
// ...
thread.wait();  // == join()
```

Qt має зручніші обгортки: `QMutexLocker` (RAII для `QMutex`), `QReadWriteLock` (для частих читань і рідкісних записів), `QSemaphore` (для обмеження кількості одночасних доступів), `QWaitCondition` (для сигналізації між потоками).

**Замість ручного управління потоками** — `std::async`:

```cpp
auto future = std::async(std::launch::async, []() {
    // фонова робота
    return result;
});
// ... інша робота ...
auto result = future.get();  // чекати завершення
```

`std::async` простіший: запустив, дістав результат пізніше. Не треба явно створювати `std::thread`, не треба думати про `join`.

**Замість потоків для паралельних обчислень** — OpenMP (для CPU-bound задач):

```cpp
#pragma omp parallel for
for (int i = 0; i < 1000000; ++i) {
    // автоматично розпаралелюється по ядрах
}
```

OpenMP — це «коментарі-підказки» компілятору, як розпаралелити цикл. Працює тільки для паралельних циклів, де кожна ітерація незалежна. Ідеально для обробки зображень, наукових обчислень, обробки великих масивів.

**Для повністю event-driven архітектури** — Qt Signals/Slots (як у Qt), або асинхронне програмування (asyncio в Python, корутини в C++20). Немає потоків — є події, обробники подій, черги. Це інша парадигма, складніша для розуміння, але безпечніша.
