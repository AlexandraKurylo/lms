# Урок 11. Де живе змінна: стек, купа, час життя

## Два світи в одній програмі

Уяви, що в тебе дві кімнати. Перша — робочий стіл: все, що зараз потрібно, лежить на ньому. Ти працюєш, потім закриваєш ноутбук — і все, що було на столі, зникає. Друга — комора: склад, куди ти складаєш речі надовго. Вони там лежать, поки ти сам не вирішиш їх викинути. Перша — це **стек** (stack), друга — **купа** (heap, heap memory).

Кожна змінна в C++ живе в одному з цих двох місць. Де саме — вирішуєш ти (іноді свідомо, іноді за замовчуванням). І від цього залежить, коли вона «помре» і хто за неї відповідає. Це, напевно, найглибша тема, яку мусить зрозуміти кожен, хто пише на C++. Після цього уроку багато речей, які раніше здавалися чорною магією, стануть очевидними.

## Стек: швидко, автоматично, локально

```cpp
void example() {
    int x = 42;        // x живе в стеку
    Word w("धर्म", "dharma", "закон");  // w живе в стеку
    // ... робимо щось ...
}  // тут x і w знищуються автоматично
```

Стек — це область пам'яті, яка росте й стискається як стос тарілок. Кожен виклик функції «кладе тарілку» (займає трохи пам'яті), кожен вихід із функції «знімає тарілку» (звільняє). Все автоматично, без твого втручання. Швидко — просто зсув покажчика стека. Передбачувано — час життя змінної точно відповідає фігурним дужкам, у яких вона оголошена.

Мінус: розмір стека обмежений (зазвичай 1–8 МБ). Плюс: змінні в стеку не треба чистити вручну, і вони завжди знищуються, навіть якщо функція виходить через виняток.

## Купа: повільно, вручну, глобально

```cpp
Word* w = new Word("धर्म", "dharma", "закон");
// ... працюємо з *w ...
delete w;  // ОБОВ'ЯЗКОВО мусимо вручну звільнити
```

Купа — це «склад», велика область пам'яті, де можна виділити місце будь-якого розміру. На відміну від стека, тут нічого не звільняється автоматично. Виділив через `new` — мусиш `delete`-нути. Забув — витік пам'яті. Викликав `delete` двічі — подвійне видалення, невизначена поведінка. Викликав `delete`, а потім звернувся до об'єкта — use-after-free, класика експлойтів.

Мінус: повільно (виділення пам'яті в купі — пошук вільного блоку), небезпечно (забув `delete` — проблема). Плюс: розмір обмежений тільки оперативною пам'яттю, час життя контролюєш ти, можна передавати об'єкти між функціями, не копіюючи.

## Код уроку

Вправа — `exercises/ex11_memory.cpp`, і вона вперше в курсі підключає справжній файл застосунку:

```cmake
add_executable(ex11_memory  exercises/ex11_memory.cpp)
```

Слово тут — той самий `Word` із `src/domain/Word.h`, який ми написали в уроці 8. Але щоб побачити час життя об'єкта на власні очі, потрібен об'єкт, який уголос повідомляє про своє народження і смерть. Тому ми не переписуємо `Word`, а **успадковуємо** його — рівно так, як учили в уроці 10: `TracedWord` **є** `Word`, просто балакучий. У самому застосунку такого логування немає й не буде: воно коштує часу і засмічує вивід.

Цей балакучий тип знадобиться ще двічі — в уроках 12 і 13, — тому одразу кладемо його в окремий заголовок, а не в тіло вправи:

```cpp
// exercises/TracedWord.h
// Word із уроку 8, який уголос повідомляє про кожну подію свого життя.
// У самому застосунку такого логування немає: воно коштує часу.
#pragma once

#include "../src/domain/Word.h"

struct TracedWord : Word {
    // Звичайне створення
    TracedWord(std::string dev, std::string tr, std::string t, int diff = 1)
        : Word(std::move(dev), std::move(tr), std::move(t), diff) {
        std::cout << "  [ctor] створено " << devanagari
                  << " за адресою " << this << "\n";
    }

    // Копіювання: новий об'єкт із власними копіями всіх трьох рядків
    TracedWord(const TracedWord& other) : Word(other) {
        std::cout << "  [copy] скопійовано " << devanagari
                  << " за адресою " << this << "\n";
    }

    ~TracedWord() {
        std::cout << "  [dtor] знищено " << devanagari << "\n";
    }
};
```

`TracedWord(std::string dev, ...) : Word(std::move(dev), ...)` — конструктор нічого не робить сам, він передає всі аргументи батьківському `Word` і додає один рядок друку. Це типова форма для класу-надбудови: не дублювати роботу базового класу, а делегувати її йому.

А ось і сама вправа:

```cpp
// exercises/ex11_memory.cpp
// Стек проти купи на справжньому Word із src/domain/Word.h.
// Збери разом із проєктом: cmake --build build
// Запусти:                 ./build/ex11_memory

#include "TracedWord.h"

// Функція, що повертає слово за значенням — без new
TracedWord makeWord() {
    TracedWord local("कर्म", "karma", "дія", 3);
    std::cout << "  [makeWord] local за адресою " << &local << "\n";
    return local;
}

int main() {
    std::cout << "=== Частина 1: автоматичне керування (стек) ===\n";
    {
        TracedWord a("धर्म", "dharma", "закон", 2);
        std::cout << "  a за адресою " << &a << "\n";
    }   // a знищується тут, автоматично
    std::cout << "--- a вже знищено ---\n\n";

    std::cout << "=== Частина 2: ручне керування (купа) ===\n";
    TracedWord* p = new TracedWord("अहिंसा", "ahimsa", "ненасильство", 4);
    std::cout << "  p зберігає адресу " << p << " (це купа)\n";
    delete p;                     // ОБОВ'ЯЗКОВО
    // delete p;                  // другий delete = невизначена поведінка
    // std::cout << p->devanagari; // use-after-free
    std::cout << "--- p звільнено ---\n\n";

    std::cout << "=== Частина 3: копія — це окремий об'єкт ===\n";
    TracedWord original("सत्य", "satya", "істина", 1);
    TracedWord copy = original;
    std::cout << "  original за " << &original
              << ", copy за " << &copy << " — різні адреси\n\n";

    std::cout << "=== Частина 4: повернення з функції ===\n";
    TracedWord returned = makeWord();
    std::cout << "  returned за " << &returned << "\n\n";

    std::cout << "=== Частина 5: витік пам'яті ===\n";
    TracedWord* leaked = new TracedWord("मोक्ष", "moksha", "звільнення", 5);
    std::cout << "  створили " << leaked->devanagari << " і загубили вказівник\n";
    // delete leaked;   <- цього рядка немає навмисно
    std::cout << "--- програма завершується; [dtor] для moksha не буде ---\n\n";

    std::cout << "=== Кінець main: знищується все, що на стеку ===\n";
    return 0;
}
```

Вивід (адреси в тебе будуть інші — пам'ятаєш ASLR з уроку 5, — але **співвідношення між ними** будуть ті самі, і саме вони тут головні):

```
=== Частина 1: автоматичне керування (стек) ===
  [ctor] створено धर्म за адресою 0000006EECF3F5B0
  a за адресою 0000006EECF3F5B0
  [dtor] знищено धर्म
--- a вже знищено ---

=== Частина 2: ручне керування (купа) ===
  [ctor] створено अहिंसा за адресою 000001CBBE5DEC50
  p зберігає адресу 000001CBBE5DEC50 (це купа)
  [dtor] знищено अहिंसा
--- p звільнено ---

=== Частина 3: копія — це окремий об'єкт ===
  [ctor] створено सत्य за адресою 0000006EECF3F530
  [copy] скопійовано सत्य за адресою 0000006EECF3F6B0
  original за 0000006EECF3F530, copy за 0000006EECF3F6B0 — різні адреси

=== Частина 4: повернення з функції ===
  [ctor] створено कर्म за адресою 0000006EECF3F630
  [makeWord] local за адресою 0000006EECF3F630
  returned за 0000006EECF3F630

=== Частина 5: витік пам'яті ===
  [ctor] створено मोक्ष за адресою 000001CBBE5DEC50
  створили मोक्ष і загубили вказівник
--- програма завершується; [dtor] для moksha не буде ---

=== Кінець main: знищується все, що на стеку ===
  [dtor] знищено कर्म
  [dtor] знищено सत्य
  [dtor] знищено सत्य
```

У цих тридцяти рядках сховано п'ять окремих фактів, і кожен варто побачити самому.

**Стек і купа — це фізично різні райони пам'яті, і це видно за адресами.** Усе, що на стеку, починається з `0000006EECF3F...` — числа відрізняються сотнями байтів. А `अहिंसा`, створене через `new`, лежить за `000001CBBE5DEC50` — інший діапазон, різниця в трильйони. Це не випадковість оформлення: стек програми виділяється при старті одним суцільним шматком, а купа живе окремо й керується аллокатором.

**`TracedWord copy = original;` справді створює другий об'єкт.** У виводі є окремий рядок `[copy]`, і адреси різні. Всередині `Word` лежать три `std::string`, кожен зі своєю пам'яттю в купі, — тож копіювання скопіювало ще й три рядки, про які в коді немає жодної згадки. Ось звідки береться «дорога копія», з якою розбиратиметься урок 13.

**RVO видно неозброєним оком.** У четвертій частині `makeWord` створює `local` за адресою `0000006EECF3F630` — і `returned` у `main` має **точно ту саму адресу**. Рядка `[copy]` між ними немає взагалі. Компілятор не створював локальний об'єкт, щоб потім його скопіювати: він одразу побудував слово там, де на нього чекає `returned`. Це називається Return Value Optimization, вона працює за замовчуванням, і з C++17 у цьому випадку навіть обов'язкова за стандартом. Тобто «повертати об'єкт за значенням — це дорого» — міф; детально в уроці 13.

**Витік видно за відсутністю рядка.** Для `मोक्ष` є `[ctor]`, але `[dtor]` немає ніде — ні відразу, ні наприкінці. Об'єкт існує, займає пам'ять, і дістатися до нього вже неможливо: єдиний вказівник на нього зник разом із завершенням `main`. Програма завершилася «успішно», з кодом 0, і ніхто не поскаржився. Ось чому витоки живуть у коді роками.

**А тепер найважливіше.** Порівняй дві адреси: `अहिंसा` у другій частині отримала `000001CBBE5DEC50`, і `मोक्ष` у п'ятій частині отримала **ту саму адресу**. Після `delete p` аллокатор позначив цей блок як вільний, і наступний же `new` віддав його новому об'єкту. Тепер уяви, що ми не видалили рядок `std::cout << p->devanagari;` після `delete`. Програма не впала б: за тією адресою лежить цілком коректний об'єкт — просто зовсім інше слово. Ти прочитав би `मोक्ष` там, де очікував `अहिंसा`, і жодного натяку на помилку. **Ось що таке use-after-free**: не аварія, а тихо підмінені дані. Аварія — це щасливий випадок, коли пощастило звернутися до сторінки, яку ОС уже забрала.

**Останні три рядки — це порядок знищення.** Об'єкти на стеку вмирають у зворотному порядку до створення: спочатку `कर्म` (створене останнім), потім обидва `सत्य` — копія, а за нею оригінал. Стек тому й називається стеком: що поклали останнім, знімається першим.

**`new` — це три операції в одному слові**: виділити пам'ять у купі під об'єкт, викликати його конструктор, повернути адресу. `delete` — дзеркальні дві: викликати деструктор і повернути пам'ять аллокатору. Проблема саме в тому, що записуються вони в різних місцях програми, часто в різних функціях і різних файлах, а компілятор не перевіряє, чи є пара. Наступний урок прибирає цю проблему разом із самим `delete`: `std::unique_ptr` не дає ані забути звільнити пам'ять, ані звернутися до вже звільненої.

## Як реально знайти витік, а не здогадуватися

Найпідступніше в усіх трьох бідах цього уроку — вони не гарантують падіння програми саме там і тоді, де сталася помилка. Замість здогадок є конкретний інструмент, вбудований у GCC, Clang і MSVC — **AddressSanitizer** (ASan). Достатньо одного прапорця при збірці:

```bash
# GCC / Clang
g++ -std=c++20 -fsanitize=address -g exercises/ex11_memory.cpp -o ex11_memory

# MSVC (Visual Studio 2019 16.9 і новіші)
cl /std:c++20 /EHsc /utf-8 /fsanitize=address /Zi exercises\ex11_memory.cpp
```

Зібрана так програма працює помітно повільніше за звичайну (тому цей прапорець ніколи не потрапляє у фінальну збірку для користувача) — але натомість миттєво, з точною вказівкою рядка коду, зупиняється на першому ж use-after-free, double-free чи витоку пам'яті, замість того щоб тихо зіпсувати дані або впасти значно пізніше в геть сторонньому місці. Розкоментуй у коді уроку рядок з другим `delete p;` або зі зверненням до `p` після видалення, збери саме з `-fsanitize=address` і подивись на справжнє повідомлення — воно назве точно той рядок, де сталася помилка, а не змусить вгадувати заднім числом.

## Де це болить у реальних проєктах

**Витоки пам'яті — це біда не тільки новачків.** Firefox років десять тому мав серйозні витоки в обробці SVG, через які браузер тримав десятки мегабайт сміття після закриття вкладки. Chrome побудував цілу архітектуру (`PartitionAlloc`, `Blink`) спеціально для боротьби з цим. Навіть у 2026 році витоки — постійна причина баг-репортів у великих проектах.

**Стек і купа — це фізично різні місця в оперативній пам'яті.** Стек зазвичай росте вниз (від високих адрес до низьких), купа — вгору. Вони можуть зустрітися посередині, і якщо це станеться — програма впаде з переповненням стека або з помилкою аллокатора. Це рідкість, але буває.

**Garbage Collector у Java/C#** — спосіб вирішити проблему «забув delete» автоматично. Програма періодично проходить усі об'єкти в купі і ті, до яких ніхто не звертається, — знищує. Зручно, але:
- GC зупиняє всю програму на час прибирання («stop the world»). У C++ нічого зупиняти не треба.
- GC не знає, що робити з нестандартними ресурсами (файлами, мережевими з'єднаннями). У C++ деструктор викликається одразу, як тільки об'єкт вийшов з-під контролю, навіть якщо це файл або сокет.
- GC вимагає рантайм. C++ — ні.

Тому в ігрових рушіях, операційних системах, вбудованих пристроях — C++ з ручним керуванням пам'яттю. У веб-бекендах — часто GC-мову, бо зручність > швидкість.

**Аналогія з орендою квартири**: стек — це тимчасове житло: заїхав, пожив, виїхав. Сплачувати окремо не треба, але й залишитися надовго не вийде, і контролювати, що відбувається в кімнаті, можна тільки поки ти всередині. Купа — це власна квартира: купив, живеш, ремонт робиш, продаєш — і ніхто, крім тебе, не вирішує, що з нею відбувається. Плюс — повний контроль. Мінус — треба самому думати про ремонт і прибирання.

## Куди це веде далі

**Замість `new`/`delete` руками** — розумні вказівники (наш наступний урок):

```cpp
// Погано: ручне керування
Word* w = new Word("धर्म", "dharma", "закон");
process(w);
delete w;  // забув = витік; delete двічі = UB

// Добре: автоматичне
auto w = std::make_unique<Word>("धर्म", "dharma", "закон");
process(w.get());
// delete не потрібен — unique_ptr сам прибере
```

**Замість `new` у купі** — контейнери STL:

```cpp
// Погано: new + ручне видалення
Word* arr = new Word[100];
// ... використання ...
delete[] arr;

// Добре: вектор сам керує
std::vector<Word> arr(100);
// ... використання ...
// нічого видаляти не треба
```

**Замість сирих вказівників у параметрах функцій** — посилання:

```cpp
// Менш безпечно
void process(Word* w) { /* може бути nullptr */ }

// Безпечніше
void process(Word& w) { /* точно існує */ }
```
