# Урок 19. Асемблер: один раз повністю

## Передмова: чому ми взагалі тут

Шість уроків ми писали на C++, два — на SIMD через інтринсики. Кожен раз — абстракція. Компілятор сам перетворює наш «людський» код на «машинний». Ми довіряємо йому. І правильно робимо. Але сьогодні ми зробимо те, що рідко хто робить у 2026 році: напишемо **асемблер** руками. Не тому, що це потрібно в реальному житті (зазвичай ні), а щоб зрозуміти, як влаштований комп'ютер під капотом.

Асемблер — це текстове подання машинних інструкцій процесора. Кожна інструкція — це рівно одна дія, яку процесор виконує за один такт. Плюс — повний контроль. Мінус — писати треба так, як думає процесор, а не як думає людина. Це як перекласти з мови високого рівня на мову дуже низького рівня, де слово «склад» — це набір із 30 нулів та одиниць.

## Код уроку

Асемблер у цьому курсі не буде окремою іграшкою «поза проєктом» — ми напишемо на ньому справжню функцію нашого застосунку й покличемо її з C++. Функція буде маленька, але не вигадана: **перетворення тексту на число**. Саме це робить читач словника з уроку 16, коли бачить у файлі `"difficultyLevel": 4` і мусить дістати звідти четвірку.

Одразу про інструмент. Класичні підручники з асемблера під x86-64 пишуть під NASM і Linux із системними викликами. Ми підемо іншим шляхом: скористаємося **MASM** — асемблером, який уже стоїть у тебе разом із Visual Studio (`ml64.exe`), і напишемо не окрему програму, а функцію, яку лінкер вкладе в наш звичайний `.exe`. Так не доведеться ставити нічого нового, і — головне — код одразу опиниться там, де він у житті й буває: усередині проєкту на C++, а не поруч із ним.

```asm
; exercises/ex19_asm/parse_level.asm
; int parseLevelAsm(const char* text)
;
; Читає з рядка десяткове число й повертає його.
; Рівно те, що робить парсер JSON, коли бачить "difficultyLevel": 4
;
; Угода про виклики Windows x64:
;   перший аргумент         -> RCX
;   значення, що повертаємо -> EAX
;   RAX, RCX, RDX, R8-R11 можна псувати вільно
;   RBX, RSI, RDI, R12-R15 треба зберігати — ми їх не чіпаємо взагалі
;
; Збери: ml64 /c /Fo parse_level.obj parse_level.asm

.code

parseLevelAsm PROC
    xor  eax, eax               ; результат = 0
    test rcx, rcx               ; вказівник нульовий?
    jz   done                   ; так -> повертаємо 0

scan:
    movzx edx, byte ptr [rcx]   ; беремо поточний символ, доповнюючи нулями
    test  dl, dl
    jz    done                  ; нульовий байт — кінець рядка
    cmp   dl, '0'
    jb    done                  ; менше за '0' — не цифра, зупиняємось
    cmp   dl, '9'
    ja    done                  ; більше за '9' — теж не цифра

    imul  eax, eax, 10          ; результат *= 10
    sub   edx, '0'              ; символ -> цифра
    add   eax, edx              ; результат += цифра
    inc   rcx                   ; наступний символ
    jmp   scan

done:
    ret                         ; результат уже в EAX
parseLevelAsm ENDP

END
```

Двадцять рядків, і в них уміщується все, що взагалі є в асемблері: регістри, порівняння, умовні переходи, звернення до пам'яті, повернення значення. А тепер покличемо це з C++:

```cpp
// exercises/ex19_asm/ex19_main.cpp

#include <iostream>
#include <iomanip>
#include <string>
#include <vector>

// extern "C" вимикає спотворення імен: без нього компілятор шукав би
// не parseLevelAsm, а щось на кшталт ?parseLevelAsm@@YAHPEBD@Z,
// і лінкер такої мітки в .asm-файлі не знайшов би.
extern "C" int parseLevelAsm(const char* text);

// Те саме на C++ — щоб було з чим порівняти
int parseLevelCpp(const char* text) {
    if (!text) return 0;
    int result = 0;
    while (*text >= '0' && *text <= '9') {
        result = result * 10 + (*text - '0');
        ++text;
    }
    return result;
}

int main() {
    // Рядки такі, якими вони приходять із файлу словника (урок 16)
    const std::vector<std::string> samples = {
        "4",                        // звичайний рівень
        "12",                       // двоцифровий
        "0",                        // нуль
        "3, \"isKnown\": false",    // число, за яким іде решта JSON
        "abc",                      // взагалі не число
        ""                          // порожній рядок
    };

    std::cout << "вхід                       asm    C++   збіг\n";
    std::cout << "--------------------------------------------\n";

    bool allMatch = true;
    for (const auto& s : samples) {
        int a = parseLevelAsm(s.c_str());
        int c = parseLevelCpp(s.c_str());
        if (a != c) allMatch = false;

        std::string shown = "\"" + s + "\"";
        if (shown.size() < 26) shown.resize(26, ' ');
        std::cout << shown
                  << std::setw(5) << a
                  << std::setw(7) << c
                  << "    " << (a == c ? "так" : "НІ") << "\n";
    }

    std::cout << "\nусі результати збігаються: " << (allMatch ? "так" : "ні") << "\n";
    std::cout << "parseLevelAsm(nullptr) = " << parseLevelAsm(nullptr) << "\n";
    return allMatch ? 0 : 1;
}
```

Збірка йде у два кроки — спершу асемблер, потім компілятор із готовим об'єктним файлом:

```bash
ml64 /c /Fo parse_level.obj exercises\ex19_asm\parse_level.asm
cl /std:c++20 /EHsc /utf-8 exercises\ex19_asm\ex19_main.cpp parse_level.obj
```

У CMake це виглядає так само буденно:

```cmake
enable_language(ASM_MASM)
add_executable(ex19_asm
    exercises/ex19_asm/ex19_main.cpp
    exercises/ex19_asm/parse_level.asm)
```

Вивід:

```
вхід                       asm    C++   збіг
--------------------------------------------
"4"                           4      4    так
"12"                         12     12    так
"0"                           0      0    так
"3, "isKnown": false"         3      3    так
"abc"                         0      0    так
""                            0      0    так

усі результати збігаються: так
parseLevelAsm(nullptr) = 0
```

Функція, написана вручну машинними інструкціями, дала рівно ті самі відповіді, що й C++, включно з граничними випадками: числом, за яким іде сміття, зовсім не числом, порожнім рядком і нульовим вказівником.

Розберемо, що тут відбувається.

**`.code` і `PROC`/`ENDP`** — розмітка файлу для MASM. `.code` каже «далі йде виконуваний код» (є ще `.data` для ініціалізованих даних і `.const` для констант). `PROC` і `ENDP` окреслюють функцію й роблять її ім'я видимим для лінкера. У NASM під Linux це записується інакше (`section .text`, `global`), але зміст той самий: код і дані лежать у різних секціях, бо операційна система дає їм різні права — код можна виконувати, але не змінювати, дані навпаки.

**Регістри.** `rax`, `rcx`, `rdx`, `r8`–`r15` та інші — це «змінні», які живуть прямо в процесорі, а не в пам'яті. Їх рівно 16, кожен на 64 біти, і саме тому доступ до них миттєвий, а до пам'яті — ні. Імена одного регістра різної ширини: `rax` — усі 64 біти, `eax` — молодші 32, `ax` — молодші 16, `al` — молодший байт. У нашому коді це видно: результат накопичується в `eax` (32 біти, бо `int`), а символ береться в `dl` (один байт).

**Угода про виклики** — найважливіше в усьому уроці, бо саме вона склеює асемблер із C++. Це домовленість, у які регістри той, хто викликає, кладе аргументи, і де шукати результат. На Windows x64 перші чотири цілочисельні аргументи йдуть у `RCX`, `RDX`, `R8`, `R9`, а результат повертається в `RAX`. На Linux і macOS домовленість інша — `RDI`, `RSI`, `RDX`, `RCX`, `R8`, `R9`. Тому той самий асемблерний файл не переноситься між системами без правок, тоді як C++ переноситься: компілятор знає обидві угоди й підставляє потрібну.

Друга частина угоди — які регістри дозволено псувати. `RAX`, `RCX`, `RDX`, `R8`–`R11` вважаються тимчасовими: викликана функція може робити з ними що завгодно. Решту (`RBX`, `RSI`, `RDI`, `R12`–`R15`) вона зобов'язана повернути такими, якими отримала. Наш код навмисно обходиться лише тимчасовими — тому в ньому немає жодного `push`/`pop`, які інакше довелося б писати для збереження чужих значень.

**`xor eax, eax`** — класичний спосіб обнулити регістр. Виглядає дивно (навіщо «виключне АБО» з самим собою?), але результат завжди нуль, а інструкція коротша й швидша за `mov eax, 0`: у ній немає константи, яку треба тягнути з пам'яті. Побачивши це в чужому коді, читай просто як «обнулити».

**`test rcx, rcx` і `jz`** — перевірка на нуль. `test` виконує логічне І й викидає результат, лишаючи тільки прапорці; `jz` (jump if zero) стрибає, якщо результат був нульовий. Разом це «якщо `rcx` дорівнює нулю — стрибай». Так само `test dl, dl` перевіряє кінець рядка, бо рядки в C закінчуються нульовим байтом.

**`movzx edx, byte ptr [rcx]`** — прочитати один байт із пам'яті за адресою в `rcx` і покласти його в `edx`, доповнивши нулями до 32 біт (`movzx` = move with zero extension). Квадратні дужки означають «за цією адресою», тобто це і є розіменування вказівника з уроку 5, тільки записане машинною мовою.

**`cmp` і умовні переходи.** `cmp dl, '0'` віднімає одне від одного, результат викидає, лишає прапорці. Далі `jb` (jump if below) стрибає, якщо перше було меншим, `ja` (jump if above) — якщо більшим. Пара `cmp` + `jb`/`ja` — це і є `if` у машинній мові, а `jmp scan` наприкінці замикає цикл. Ніяких `while` у процесора немає: будь-який цикл — це порівняння і стрибок назад.

**`sub edx, '0'`** — символ мінус код нуля дає саму цифру: `'5'` це 53, `'0'` це 48, різниця 5. Той самий трюк, що й у C++ рядку `(*text - '0')`, тільки видно, що це справді просто віднімання.

## А тепер подивимось, що з нашого C++ зробив компілятор

Найкорисніша частина уроку — не написати асемблер, а **прочитати** його. Попроси компілятор показати, у що він перетворив `parseLevelCpp`:

```bash
cl /std:c++20 /O2 /FAs /Fa. exercises\ex19_asm\ex19_main.cpp
```

Ключ `/FAs` створює файл `.asm` із листингом, де поруч із машинними інструкціями стоять рядки твого коду. У GCC і Clang те саме робить `-S`. Ось що вийшло в мене:

```asm
?parseLevelCpp@@YAHPEBD@Z PROC              ; parseLevelCpp, COMDAT
        mov     r8, rcx
        test    rcx, rcx
        jne     SHORT $LN4@parseLevel
        xor     eax, eax
        ret     0
$LN4@parseLevel:
        movzx   eax, BYTE PTR [r8]
        xor     ecx, ecx
        cmp     al, 48                      ; 00000030H
        jl      SHORT $LN3@parseLevel
$LL2@parseLevel:
        cmp     al, 57                      ; 00000039H
        ja      SHORT $LN3@parseLevel
        lea     edx, DWORD PTR [rcx+rcx*4]
        inc     r8
        movzx   ecx, al
        movzx   eax, BYTE PTR [r8]
        lea     ecx, DWORD PTR [rcx+rdx*2]
        add     ecx, -48                    ; ffffffffffffffd0H
        cmp     al, 48                      ; 00000030H
        jge     SHORT $LL2@parseLevel
$LN3@parseLevel:
        mov     eax, ecx
        ret     0
?parseLevelCpp@@YAHPEBD@Z ENDP
```

Перше, що впадає в око, — **ім'я функції**: `?parseLevelCpp@@YAHPEBD@Z`. Ось воно, те саме спотворення імен, заради якого в оголошенні асемблерної функції стоїть `extern "C"`. У цьому рядку зашифровано: це функція, вона повертає `int` (`H`), приймає вказівник на константний `char` (`PEBD`). Компілятор шифрує типи в ім'я, щоб дві функції з однаковою назвою й різними параметрами не зіткнулися при лінкуванні — без цього перевантаження функцій у C++ було б неможливим. Наша асемблерна функція такого шифру не має, тому й потрібне `extern "C"`.

Друге — **порівняй із тим, що написали ми**. У нашому асемблері множення на десять зроблено чесним `imul eax, eax, 10`. Компілятор `imul` не використав узагалі: він написав `lea edx, [rcx+rcx*4]` (це `rcx * 5`), а потім `lea ecx, [rcx+rdx*2]` (додати подвоєне, тобто разом `× 10`). Інструкція `lea` формально призначена для обчислення адрес, але вміє за один такт складати й множити на 2, 4 чи 8, — і компілятори користуються нею для арифметики, бо вона швидша за справжнє множення.

Третє — компілятор **побудував цикл інакше**, ніж ми: він читає наступний символ і порівнює його ще до стрибка назад, щоб на кожній ітерації був лише один перехід замість двох. Це називають ротацією циклу, і робиться воно рівно для того, щоб процесору було легше передбачати розгалуження.

Чесний висновок наостанок. Наша асемблерна функція працює правильно і робить те саме, але **писати такий код руками заради швидкості сенсу немає** — компілятор із `/O2` майже завжди зробить не гірше, а частіше краще, бо тримає в голові конвеєр, кеш і таблиці затримок конкретної мікроархітектури. Асемблер сьогодні пишуть руками у трьох випадках: коли потрібної інструкції немає в мові взагалі (криптографія, атомарні примітиви, робота з прапорцями процесора), коли потрібна гарантія часу виконання до такту, і коли компілятора просто немає — на етапі завантаження системи. Але **читати** асемблер доводиться значно частіше: коли програма впала в користувача, а в тебе є тільки краш-дамп без символів налагодження, і треба зрозуміти, що саме там сталося.

## Де це реально використовується

**Операційна система Linux** — це мільйони рядків C і асемблера. Архітектурно-залежний код (arch/x86/) — це асемблер. Обробники переривань, контекстне переключення між процесами, початкове завантаження (boot) — все це асемблер. C використовується там, де асемблер занадто багатослівний, але ядро без асемблера не існує.

**Вбудовані системи** — мікроконтролери часто програмують на асемблері (або на C, але з асемблерними вставками для критичних частин). У промисловому контролері, в автомобільній системі, в побутовій техніці — асемблер живе там, де кожен такт має значення, а пам'ять вимірюється в кілобайтах.

**Криптографія** — деякі криптографічні алгоритми реалізують на асемблері, щоб бути стійкими до таймінгових атак (коли атакуючий вимірює час виконання і з цього витягує секретний ключ). «Константний час» на C майже неможливо гарантувати, на асемблері — можна.

**Reverse engineering** — аналіз чужого коду (без вихідного) починається з асемблера. Дизасемблери (IDA, Ghidra, radare2) показують інструкції, і реверс-інженер читає їх, як ми читаємо текст. Навіщо? Щоб зрозуміти, як працює шкідливе ПЗ, знайти вразливість, відновити втрачений код. Знання асемблера — обов'язкова навичка в кібербезпеці.

**Аналогія з кухнею**: C++ — це рецепт із книжки («додайте 200 г борошна, 100 г цукру»). Асемблер — це інструкція для комбайна на заводі: «подати 200 грамів із бункера 3, перемішати з 100 грамами з бункера 7, нагріти до 180 градусів протягом 15 секунд». Набагато точніше, набагато більше роботи, набагато більше шансів помилитися. Але коли тобі треба випекти 10 000 тістечок за годину — без інструкції для комбайна не обійтися.

## Куди це веде далі

**Замість асемблера x86-64** — ARM (мобільні пристрої, Apple M-серія), RISC-V (нова відкрита архітектура), MIPS (старі роутери). Принципи ті самі, синтаксис інший.

**Замість MASM** — NASM (найпоширеніший у навчальних матеріалах, працює скрізь, синтаксис близький до MASM), GAS (стандартний у GNU, синтаксис дзеркальний: `mov src, dst` замість `mov dst, src`), FASM. Файл `.asm`, написаний під один асемблер, під інший зазвичай не збирається без правок — на відміну від `.cpp`.

**Замість написання асемблера руками** — компілятор зробить це за тебе з C/C++. Увімкни `-S` (або `/FA` для MSVC) і отримаєш асемблерний лістинг. Для розуміння, як компілятор оптимізує, це краще, ніж писати самому.

**Для навчання** — книги: «Programming from the Ground Up» (Jonathan Bartlett), «Assembly Language» (Kip Irvine). Курси на Coursera, edX. Головне — практика: написав, зібрав, запустив, подивився, що вийшло, виправив, повторив.

## Питання для самоперевірки

1. Збери й запусти вправу. Додай до списку `samples` рядок `"999999999999"` — що поверне асемблерна версія і що C++? Поясни, чому обидві дають те саме неправильне число.
2. Додай у `parse_level.asm` обробку від'ємних чисел: якщо перший символ `-`, пропусти його, а результат наприкінці зроби від'ємним (інструкція `neg eax`). Не забудь додати такий самий випадок у C++-версію, інакше перевірка на збіг перестане проходити.
3. Заміни в асемблері `imul eax, eax, 10` на пару інструкцій `lea`, як це зробив компілятор. Перевір, що результати не змінилися.
4. Прибери `extern "C"` з оголошення функції в C++ і збери. Прочитай повідомлення лінкера — яке саме ім'я він шукає і чому не знаходить?
5. Зроби листинг (`/FAs`) для функції `daysUntilNextReview` з уроку 4. У що перетворився `switch` — у ланцюжок порівнянь чи в таблицю переходів? Спробуй пояснити, чому компілятор обрав саме це.
6. Зроби листинг для `countHardScalar` з уроку 18, зібраної з `/O2 /arch:AVX2`. Знайди в ньому інструкції, що починаються на `vp` — це і є та сама автовекторизація, про яку йшлося в тому уроці.
