# Урок 2. Збираємо робоче місце

У попередньому житті, до того як ти вирішив писати на C++, ти напевно запускав готові `.exe`-файлики і не замислювався, як вони з'являються. У C++ ти мусиш зрозуміти цей процес сам, інакше все подальше нагадуватиме кулінарію за рецептом, де тобі не сказали, як увімкнути плиту.

Перш ніж ставити щось на комп'ютер, варто знати одну річ, яку індустрія не любить проговорювати вголос: **компілятор** і **середовище розробки (IDE)** — це дві абсолютно різні речі, і новачки їх майже завжди плутають. Компілятор — програма, яка читає твій `.cpp`-файл і перетворює його на машинний код. IDE — просто зручна оболонка навколо нього: підсвічування синтаксису, кнопка «Збірка», вбудований дебагер. Гарна приладова панель навколо одного й того самого двигуна. Якщо ти поставиш повну Visual Studio або легкий VS Code з окремо довантаженими інструментами збірки — в обох випадках компілювати код на Windows буде рівно той самий MSVC (`cl.exe`), захований десь у системі. Різні кнопки, той самий двигун.

## Що встановлювати

**Windows (наш основний шлях):** Visual Studio Community Edition, безкоштовна. При встановленні вибери робоче навантаження **«Розробка класичних застосунків на C++»** — воно підтягне MSVC і Windows SDK. Додатково познач вручну ще дві речі, яких немає в навантаженні за замовчуванням: **C++ CMake tools for Windows** (без нього далі не зрушитися) і **English language pack** — навіть якщо решта системи в тебе українською. Причина суто практична: коли компілятор видасть помилку (а видасть, і не раз), її доведеться гуглити, а весь світ обговорює саме англійські формулювання помилок.

**Linux:** `sudo apt install build-essential cmake ninja-build` (Ubuntu/Debian) або `sudo pacman -S base-devel cmake ninja` (Arch). Компілятор тут — GCC, і його тексти помилок відрізняються від MSVC не лише назвою.

**macOS:** `xcode-select --install` дає компілятор Clang, `git` і `make`. Далі `brew install cmake ninja` для решти інструментів.

**CLion** (JetBrains, платно з тріалом, безкоштовно для студентів) — окремий випадок: сама CLion компілятора не приносить, вона питає, яким саме інструментом збирати. На Windows це може бути той самий MSVC — тоді все, як і вище, — а може бути MinGW, окремий GCC-сумісний компілятор для Windows, який видає інші тексти помилок на той самий код. Для старту простіше уникнути цієї зайвої розвилки.

Я не вдаватиму, що однаково добре знаю всі платформи. Далі в курсі команди даю для MSVC (основний шлях) і GCC/Clang (Linux/macOS) паралельно.

## Чому не просто `cl` чи `g++`, а CMake

Компілятор можна викликати і напряму — `cl main.cpp` або `g++ main.cpp -o main` — і колись ми саме так і зробимо, щоб побачити, що там усередині немає магії. Але щойно у проєкті з'явиться другий файл, а потім бібліотека з власними шляхами до заголовків — рядок виклику компілятора перетворюється на нечитабельний абзац, де одна одруківка ламає все. Тому реальні проєкти на C++ (і наш SAMSKRTA теж) описують збірку один раз декларативно, а компілятор викликають не напряму.

Це і робить **CMake** — не компілятор, а генератор: він читає один файл `CMakeLists.txt` і сам створює те, що потрібно твоєму оточенню — рішення Visual Studio на Windows, `Makefile` на Linux, файли для швидкого `Ninja`, якщо попросиш. Створи папку проєкту (без пробілів і кирилиці в шляху — це гарантований спосіб зловити загадкову помилку лінкера о третій ночі), а всередині — підпапку `src`. У корені створи `CMakeLists.txt`:

```cmake
cmake_minimum_required(VERSION 3.21)
project(samskrta LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

if(MSVC)
    add_compile_options(/W4 /WX)
else()
    add_compile_options(-Wall -Wextra -Werror)
endif()

add_executable(samskrta src/main.cpp)
```

`CMAKE_CXX_STANDARD_REQUIRED ON` забороняє компілятору мовчки «відкотитися» на старіший стандарт, якщо C++20 не підтримується повністю — краще зрозумілий збій зараз, ніж дивний баг потім. Блок `if(MSVC)` вмикає максимальну строгість попереджень на кожному компіляторі своїм прапорцем (`/W4 /WX` для MSVC, `-Wall -Wextra -Werror` для GCC/Clang) — і одразу перетворює попередження на помилки збірки. Це не занудство: попередження компілятора майже завжди вказують на реальний баг чи невизначену поведінку, і привчати себе ігнорувати їх з першого дня — прямий шлях до довгого дебагу пізніше.

Запусти генерування з кореня проєкту:

```bash
cmake -B build -S .
```

Файлу `src/main.cpp` у нас іще немає, тож CMake чесно про це скаже:

```
CMake Error at CMakeLists.txt:13 (add_executable):
  Cannot find source file:
    src/main.cpp
```

Це вже перемога, а не провал: CMake вказав точний рядок і точну причину. `-B build` означає «склади всі проміжні файли в окрему папку `build`», а не в корінь проєкту (**out-of-source build**) — якщо колись треба буде «все спочатку», просто видаляєш папку `build` цілком, не чіпаючи жодного вихідника.

Створи `src/main.cpp` з кодом уроку 1, згенеруй знову — цього разу без помилок — і збери:

```bash
cmake --build build
```

Готовий `samskrta.exe` (чи `samskrta` на Linux) з'явиться в `build/Debug` (Windows) або просто в `build/` (Linux). Якщо хочеться швидшої збірки — можна попросити CMake згенерувати файли під Ninja замість Visual Studio: `cmake -G "Ninja" -B build -S .` після видалення старої папки `build`.

## Помилка, яку ти зробиш точно

Тепер, коли є на чому будувати, спробуй зламати щось навмисно. Створи `bug.cpp` поруч і встав його в `add_executable` замість `main.cpp`:

```cpp
#include <iostream>

int main() {
    std::cout << "Привіт, C++!" << std::endl
    return 0;
}
```

Крапка з комою пропущена свідомо. Збери — отримаєш щось на кшталт:

```
bug.cpp(5): error C2143: syntax error: missing ';' before 'return'
```

Це компілятор лає тебе, але не як людина, а як робот-бюрократ: точно, сухо, з координатами місця злочину. `bug.cpp(5)` — файл і рядок, де він зупинився, `C2143` — код помилки (гуглиться, запам'ятовувати не треба). Це перше, чого варто навчитися: **читати помилки компілятора, а не панікувати від них**.

Інша класична помилка — забутий `#include`. Прибери `#include <iostream>`:

```cpp
int main() {
    cout << "Привіт" << endl; // cout і endl невідомі без заголовка
    return 0;
}
```

Помилка буде приблизно `cout: undeclared identifier`. Компілятор не знає, що таке `cout`, — ти ж не сказав йому, де це шукати. Це як прийти в ресторан і попросити «ту саму штуку, що минулого разу» — офіціант не зобов'язаний пам'ятати.

## Код уроку: аргументи командного рядка

А тепер додамо в `main.cpp` дещо корисне — власний «Hello, Build!» з аргументами командного рядка, щоб побачити, як програма й термінал спілкуються:

```cpp
// src/main.cpp
#include <iostream>
#include <string>

bool isValidName(const std::string& name) {
    return !name.empty() && name.length() <= 50;
}

int main(int argc, char* argv[]) {
    // argc — кількість аргументів, argv — сам масив (argv[0] — ім'я програми)
    std::string name;

    if (argc > 1) {
        name = argv[1];               // ім'я передали через командний рядок
    } else {
        std::cout << "Введи своє ім'я: ";
        std::getline(std::cin, name); // ім'я не передали — питаємо
    }

    if (!isValidName(name)) {
        std::cerr << "Помилка: ім'я має бути від 1 до 50 символів.\n";
        return 1; // ненульовий код = щось пішло не так
    }

    std::cout << "Привіт, " << name << "! Компілятор тебе бачить.\n";
    return 0;
}
```

```bash
cmake --build build
./build/samskrta Остап
# або просто ./build/samskrta без аргументів
```

`int main(int argc, char* argv[])` — розширена версія `main`. Коли пишеш `./samskrta Остап`, `argc` стає `2` (сама програма + один аргумент), а `argv[1]` — рядок `"Остап"`. Це як передати записку через вікно: усе після імені програми — текст записки.

`bool isValidName(const std::string& name)` — перша власна функція, приймає рядок за **константним посиланням** (`const std::string&`): «дай доступ до рядка, але я його не змінюю і не копіюю зайвий раз». Копіювання рядка при кожному виклику коштує пам'яті й часу — в маленькій програмі непомітно, у великій відчутно. Детальніше — в уроці 5.

`std::cerr` — окремий потік для помилок, не буферизується і не змішується з основним виводом при перенаправленні (`./samskrta > out.txt` — звичайний текст піде у файл, повідомлення про помилку все одно з'явиться в консолі). `return 1;` за домовленістю означає «щось пішло не так» — скрипти, що викликають твою програму, можуть перевірити це число, не читаючи жодного тексту.

## Ця папка — не одноразова вправа

Тримай у голові одну річ до кінця курсу: `samskrta/` і `src/main.cpp`, які ти щойно створив, — не разова демка, яку можна викинути після уроку. Це зародок того самого застосунку, який ми будуємо весь курс. Урок 7 перепише вміст `main.cpp` на справжнє Qt-вікно — і вже назавжди, урок 8 додасть до цього дерева `src/domain/Word.h`, урок 9 — `src/data/Database.h`, і так по черзі. `CMakeLists.txt` теж не переписується щоразу з нуля — до нього просто дописується новий рядок, коли з'являється новий файл.

Створи поруч із `src` ще одну папку — `exercises`. Туди підуть уроки, які ставлять один точковий експеримент: подивитися, як переповнюється лічильник, як `std::move` уникає копіювання, наскільки AVX2 швидший за звичайний цикл. Кожна така вправа — окрема маленька програма з власним `main()`, і в CMake вона теж окремий рядок:

```cmake
add_executable(samskrta       src/main.cpp)
add_executable(ex03_numbers   exercises/ex03_numbers.cpp)
```

Це нормальна практика, а не навчальна умовність: у справжніх проєктах на C++ поруч із головним таргетом майже завжди живуть допоміжні — `tests`, `benchmarks`, `examples`. Збирається все однією командою `cmake --build build`, а запускається окремо: `./build/samskrta` — застосунок, `./build/ex03_numbers` — вправа.

Різниця між двома папками одна, і вона важлива. Файли з `src/` **входять у застосунок** і більше не переозначуються: написали `Word` в уроці 8 — далі всі беруть саме його. Файли з `exercises/` у застосунок не входять, але працюють із тими самими даними, що й він (рівні складності слів, кількість повторень, деванагарі-рядки), а починаючи з уроку 11 — прямо підключають заголовки з `src/`. Тобто вправа — це не «задачка з підручника про кошенят», а експеримент над твоїм власним застосунком, винесений в окремий файл, щоб не засмічувати робочий код виводом у консоль.

## Що там насправді під CMake

Кожен серйозний проєкт на C++ проходить ті самі два кроки: компілятор перетворює кожен `.cpp` на об'єктний файл (`.obj`/`.o`), лінкер склеює їх в один виконуваний файл. У Windows `cl.exe` часто робить обидва кроки непомітно за один виклик; у Linux їх видно окремо:

```bash
g++ -c main.cpp      # main.cpp -> main.o
g++ -c utils.cpp     # utils.cpp -> utils.o
g++ main.o utils.o -o program   # лінкер: *.o + бібліотеки -> program
```

CMake саме цю рутину і ховає за одним рядком `add_executable(samskrta src/main.cpp)` — а щойно файлів стане п'ятдесят чи додасться зовнішня бібліотека з власними шляхами до заголовків, різниця між «одним рядком CMake» і «нечитабельним абзацем ручного виклику» стає відчутною фізично, а не теоретично.

Аналогія з музикою: компілятор — композитор, що перекладає партитуру (твій код) у ноти, зрозумілі оркестру (процесору). Лінкер — диригент, що збирає всіх музикантів і каже «грайте». Кожен `.cpp` файл — партія окремого інструмента; без диригента кожен грає своє, і виходить каша. Unreal Engine має близько 100 000 файлів вихідного коду, і повна збірка займає години — тому в Epic побудували систему, яка розподіляє компіляцію різних частин по різних машинах паралельно. Без розуміння, що таке компілятор і лінкер, ти б навіть не зрозумів, як таке взагалі можливо технічно.

Системи збірки, крім CMake, теж існують: **Meson** — приємніший синтаксис, використовується в збірці GNOME і плеєра MPV, але менш поширений. **Bazel** — від Google, потужний для гігантських монорепозиторіїв, крива входу як у сноуборду на Еверест. **Make** — дідусь родом іще з Unix сімдесятих, працює й досі, але писати на ньому новий проєкт у 2026-му — як свідомо обирати друкарську машинку. CMake переміг не тому, що найкращий у всіх суперечках про синтаксис (їх достатньо), а тому що 95% бібліотек C++ у світі вже описані саме через нього.

**Питання для самоперевірки**

1. Прибери `/WX` (або `-Werror`) з `CMakeLists.txt` і навмисно залиш у коді змінну, яка ніде не використовується. Збери. Що зміниться в поведінці збірки?
2. Спробуй навмисно зробити три різні помилки: забути `;`, забути `#include`, написати неіснуюче ім'я змінної. Які з них ловить компілятор, а які — ні?
3. Чим відрізняється `std::cout` від `std::cerr`? Коли який використовувати?
4. Запусти `./samskrta "Остап Бендер"` (у лапках) і без лапок. Що станеться з пробілом у імені в кожному випадку? Чому саме так?
5. Видали папку `build` і згенеруй проєкт заново з `-G "Ninja"` замість генератора Visual Studio за замовчуванням. Що змінилося у файлах, які створив CMake?
