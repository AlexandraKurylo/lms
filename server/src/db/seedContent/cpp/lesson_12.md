# Урок 12. Розумні вказівники: компілятор стежить за тобою

## Чому ми ненавидимо `delete`

Після минулого уроку ти мав побачити, що ручне керування пам'яттю — це суцільний біль. Кожен `new` треба пам'ятати і парний `delete`. Забув — витік. Викликав двічі — невизначена поведінка. Забув, що хтось інший уже видалив, — use-after-free. Це як ходити по мінному полю, де ти сам же і закопав міни.

Сьогодні ми це виправимо. **Розумні вказівники** (smart pointers) — це маленькі обгортки, які поводяться як звичайні вказівники, але самі стежать за часом життя об'єкта. Звільняти пам'ять уручну більше не потрібно. Звучить як магія, але це просто RAII — та сама техніка, яку ми вже бачили з `std::lock_guard` у минулому уроці. Деструктор розумного вказівника сам викликає `delete`. Все.

## Три розумних вказівники

**`std::unique_ptr<T>`** — володіє об'єктом один. Ніхто інший не має права володіти. Не можна копіювати, тільки переміщати. Коли `unique_ptr` знищується — об'єкт знищується автоматично. Це те, що ти використовуватимеш у 90% випадків.

**`std::shared_ptr<T>`** — володіє об'єктом разом із іншими `shared_ptr`. Усі тримають лічильник посилань. Коли останній `shared_ptr` знищується — об'єкт знищується. Зручно, коли об'єкт справді потрібен у кількох місцях одночасно.

**`std::weak_ptr<T>`** — «погляд» на об'єкт, яким володіє `shared_ptr`, але без участі в лічильнику. Щоб скористатися, треба «підвищити» до `shared_ptr` через `.lock()`. Якщо об'єкт уже знищений — `.lock()` поверне `nullptr`. Використовується для розв'язання циклів у посиланнях.

Для 90% ситуацій вистачає `unique_ptr`. Почнемо з нього.

## Код уроку

Вправа — `exercises/ex12_smart.cpp`, і вона бере той самий `TracedWord`, що ми зробили в уроці 11: файл `exercises/TracedWord.h` уже лежить у проєкті, переписувати його не треба.


Головне, на що варто дивитися далі: у всьому файлі **немає жодного `delete`**, а кожен `[ctor]` усе одно має свій `[dtor]`.

```cpp
// exercises/ex12_smart.cpp
// Розумні вказівники над тим самим словом. Жодного delete в коді.
// Збери разом із проєктом: cmake --build build
// Запусти:                 ./build/ex12_smart

#include <memory>
#include "TracedWord.h"

// Фабрика: повертає unique_ptr — типовий сучасний C++
std::unique_ptr<TracedWord> makeWord(std::string dev, std::string tr,
                                     std::string t, int diff) {
    return std::make_unique<TracedWord>(std::move(dev), std::move(tr),
                                        std::move(t), diff);
}

// Приймає володіння: після виклику вказівник у того, хто викликав, порожній
void consume(std::unique_ptr<TracedWord> w) {
    std::cout << "  [consume] прийняла володіння " << w->devanagari << "\n";
}   // об'єкт знищується тут

// Просто дивиться, володіння не бере
void inspect(const Word& w) {
    std::cout << "  [inspect] бачить " << w.devanagari
              << ", рівень " << w.difficultyLevel << "\n";
}

int main() {
    std::cout << "=== unique_ptr: рівно один власник ===\n";
    {
        auto w1 = std::make_unique<TracedWord>("धर्म", "dharma", "закон", 2);
        std::cout << "  w1 тримає адресу " << w1.get() << "\n";
        inspect(*w1);

        // auto w2 = w1;          // помилка компіляції: копіювати не можна
        auto w2 = std::move(w1);  // переміщення: володіє w2, w1 порожній
        std::cout << "  після move: w1 " << (w1 ? "щось тримає" : "порожній") << "\n";
        std::cout << "  після move: w2 тримає адресу " << w2.get() << "\n";
    }   // тут w2 виходить з області видимості — і delete стається сам
    std::cout << "--- вийшли з блоку, delete не писали ---\n\n";

    std::cout << "=== фабрика і передача володіння ===\n";
    {
        auto w = makeWord("कर्म", "karma", "дія", 3);
        consume(std::move(w));
        std::cout << "  після consume: w " << (w ? "щось тримає" : "порожній") << "\n";
    }
    std::cout << "\n";

    std::cout << "=== shared_ptr: спільне володіння ===\n";
    {
        auto s1 = std::make_shared<TracedWord>("सत्य", "satya", "істина", 1);
        std::cout << "  лічильник власників: " << s1.use_count() << "\n";
        {
            auto s2 = s1;   // копіювання дозволене, об'єкт той самий
            std::cout << "  після s2 = s1: " << s1.use_count() << "\n";
            std::cout << "  s1 і s2 тримають ту саму адресу: "
                      << (s1.get() == s2.get() ? "так" : "ні") << "\n";
        }   // s2 знищується, лічильник зменшується
        std::cout << "  після знищення s2: " << s1.use_count() << "\n";
    }   // лічильник дійшов до нуля — тільки тут знищується сам об'єкт
    std::cout << "\n";

    std::cout << "=== weak_ptr: спостерігач без володіння ===\n";
    std::weak_ptr<TracedWord> watcher;
    {
        auto owner = std::make_shared<TracedWord>("अहिंसा", "ahimsa", "ненасильство", 4);
        watcher = owner;   // weak_ptr не збільшує лічильник
        std::cout << "  лічильник власників: " << owner.use_count()
                  << "   <- weak_ptr його не змінив\n";
        if (auto locked = watcher.lock()) {
            std::cout << "  lock() поки живий: " << locked->devanagari << "\n";
        }
    }
    if (auto locked = watcher.lock()) {
        std::cout << "  lock() після смерті: " << locked->devanagari << "\n";
    } else {
        std::cout << "  lock() після смерті: порожньо, і програма це помітила\n";
    }

    std::cout << "\n=== словник як вектор unique_ptr ===\n";
    {
        std::vector<std::unique_ptr<TracedWord>> dict;
        dict.push_back(makeWord("मोक्ष", "moksha", "звільнення", 5));
        dict.push_back(makeWord("योग", "yoga", "єднання", 1));
        for (const auto& w : dict) {
            inspect(*w);
        }
        std::cout << " -- кінець блоку: знищується вектор --\n";
    }   // вектор -> кожен unique_ptr -> кожне слово

    std::cout << "\n=== Кінець main ===\n";
    return 0;
}
```

Порахуй `[ctor]` і `[dtor]` у цьому виводі: їх порівну. А тепер згадай урок 11, де один `[dtor]` бракував, бо ми забули `delete`. Різниця в тому, що забути тут нема чого — рядка `delete` у файлі немає взагалі.

Найважливіший рядок у першому блоці — той, де після `std::move` адреса **не змінилася**: `w2` тримає ту саму `0000017AFDAE83F0`, що тримав `w1`. Слово не переїжджало нікуди й не копіювалося; переїхало тільки право його видалити. Тому переміщення `unique_ptr` коштує стільки ж, скільки присвоєння одного числа.

У блоці з `consume` подивись на порядок: `[dtor]` для `कर्म` надрукувався **до** рядка «після consume». Функція забрала володіння, і слово померло разом із кінцем функції — а не тоді, коли закінчився блок у `main`. Це і є передача володіння, видима на секунду.

Розберемо решту.

**`std::make_unique<Word>(...)`** — функція-фабрика, яка в одному виразі виділяє пам'ять і створює об'єкт. Безпечніша за `std::unique_ptr<Word>(new Word(...))`, бо в останньому можливий виняток у конструкторі, і `new` вже виділив пам'ять, яку ніхто не прибрав. `make_unique` такого не допускає.

**`auto w2 = std::move(w1);`** — переміщення. Після `move` об'єкт `w1` порожній, `w2` володіє. Це не копіювання, це «передача володіння». Працює швидко — просто копіюється вказівник, без виділення нової пам'яті. Детально про move-семантику — у наступному уроці.

**`s1.use_count()`** — лічильник посилань. Кожне копіювання `shared_ptr` збільшує на 1, кожне знищення — зменшує. Коли доходить до 0, об'єкт знищується. Це схоже на те, як клубок ниток розмотується, коли всі відрізки відірвані — залишок сам падає.

**`weak_ptr::lock()`** — спроба «підвищити» `weak_ptr` до `shared_ptr`. Якщо об'єкт живий — отримуєш `shared_ptr` (звичайний доступ). Якщо об'єкт помер — отримуєш `nullptr`. Це дозволяє безпечно спостерігати, не запобігаючи знищенню. Без `weak_ptr` була б класична проблема: двоє `shared_ptr` посилаються одне на одного, лічильник ніколи не доходить до 0, і об'єкти «висять» у пам'яті вічно.

**`std::vector<std::unique_ptr<Word>>`** — вектор володіє вказівниками, кожен вказівник володіє об'єктом. Коли вектор знищується — всі його елементи теж. Кожен `unique_ptr` знищується — відповідний `Word` знищується. Ланцюжок, який не можна перервати (хіба що випадково викликати `release()` і забути видалити). Ідеально для словника — ти можеш додавати, видаляти, переміщати слова, і ні один не витече.

**`w->devanagari` vs `(*w).devanagari`** — оператор `->` — це просто синтаксичний цукор. `w->devanagari` рівно те саме, що `(*w).devanagari`: розіменуй вказівник, звернися до поля. Стрілочка існує тільки для зручності — бо інакше код з вказівниками виглядає як `(*ptr).field().subfield().method()`, що не дуже приємно.

## unique_ptr чи батько Qt — як обирати

В уроці 7 з'явився інший спосіб керувати часом життя — батьківське володіння Qt (`new QPushButton("Далі", &window)`), де об'єкт видаляється сам, коли вмирає його батько. Тепер, коли є `unique_ptr`, варто розібратися, коли брати що. Правило просте: якщо час життя об'єкта природно збігається з часом життя його логічного «господаря» (кнопка живе, поки живе вікно) — бери батька Qt. Якщо об'єкт має створюватися й знищуватися багаторазово за власним розкладом, незалежно від інших об'єктів навколо (наприклад, буфер озвучки, який перестворюється щоразу заново) — бери `unique_ptr`. Змішувати обидва способи для одного й того самого об'єкта не варто ніколи: якщо в конструктор одночасно передати і Qt-батька, і покласти вказівник у `unique_ptr`, обидва механізми спробують видалити об'єкт, і це подвійне звільнення з уроку 11, тільки замасковане під акуратний код.

## Де це вже прийнято як стандарт

**Google Style Guide** категорично забороняє сирі вказівники-власники в новому коді C++. Уся команда Google (і в Chromium, і в Android, і в TensorFlow) пише з `std::unique_ptr` і `absl::WrapUnique` (аналог з Abseil). Якщо в тебе є `T*` як поле класу, це сигнал: «цей код треба переписати на `unique_ptr<T>`».

**Qt має власні розумні вказівники**: `QScopedPointer` (аналог `unique_ptr`), `QSharedPointer` (аналог `shared_ptr`), `QWeakPointer` (аналог `weak_ptr`). У Qt 6 вони повністю сумісні з std-версіями, можна конвертувати.

**Rust** пішов далі: там розумні вказівники — це нормa, а сирі вказівники треба спеціально позначати як `unsafe`. C++ — на півдорозі: розумні є, але сирі нікуди не поділися, і за правильне їх використання відповідає програміст.

**Циклічні посилання** — класична пастка `shared_ptr`. Уяви: `Parent` має `shared_ptr<Child>`, `Child` має `shared_ptr<Parent>`. Створив `Parent` — лічильник = 1. Створив `Child` всередині нього — `Parent` лічильник = 2. Вийшов із зовнішньої функції — `Parent` лічильник = 1, `Child` лічильник = 1. Об'єкти живуть вічно, хоча ти їх не використовуєш. Рішення — одна з ланок циклу має бути `weak_ptr`. Це класична причина, чому `shared_ptr` не панацея, і в новому коді зазвичай починають з `unique_ptr` і переходять на `shared_ptr` тільки при реальній потребі.

**Аналогія з орендою**: сирий вказівник — це ключі від чужої квартири, які тобі тимчасово дали. Ти можеш повернутися в будь-який момент, навіть якщо власник уже виїхав і здав ключі іншому. `unique_ptr` — це власна квартира: вона в тебе, і коли ти переїдеш, вона звільниться автоматично. `shared_ptr` — це спільна оренда з другом: поки хоча б один із вас живе там, квартира існує. `weak_ptr` — це сусід, який знає, що ви там живете, але не має ключів — і навіть не заперечує, якщо ви поїхали.

## Куди це веде далі

**Замість `std::unique_ptr`** у Qt-проектах — `QScopedPointer` (легший) або звичайний `std::unique_ptr` (Qt 6 повністю підтримує STL).

**Замість ручного створення колекцій об'єктів** — у Qt є `QList<std::unique_ptr<T>>`, у Boost — `boost::ptr_vector`. Це контейнери, які вміють володіти вказівниками напряму, без `unique_ptr` вручну (хоча `std::vector<std::unique_ptr<T>>` цілком нормальний).

**Замість `shared_ptr` через циклічні структури** — `weak_ptr` або повне перепроєктування ієрархії. Якщо у тебе цикл — можливо, тобі не потрібен `shared_ptr`, можливо, потрібна інша модель володіння.

## Питання для самоперевірки

1. Заміни `auto w1 = std::make_unique<Word>(...)` на `Word* w1 = new Word(...)`. Додай `delete w1` вручну. Запусти під valgrind. Що змінилося?
2. Спробуй скопіювати `unique_ptr`: `auto w2 = w1;`. Що каже компілятор? Чому так?
3. Поясни, чому `shared_ptr` повільніший за `unique_ptr`. Згадай лічильник посилань.
4. Створи дві структури, `Parent` і `Child`, де `Parent` має `shared_ptr<Child>`, а `Child` — `shared_ptr<Parent>`. Створи екземпляр у функції, вийди з функції. Перевір лічильники. Чому вони не падають до 0?
5. Перепиши `consume()` так, щоб вона не забирала володіння, а тільки дивилася на об'єкт. Який тип параметра?
