# Урок 20. Вайб-кодинг: те, що ти пишеш моделі, важливіше за те, що вона пише тобі

Дев'ятнадцять уроків ти писав кожен рядок сам. Компілятор кричав на тебе простирадлами помилок, ти ловив витоки пам'яті, розбирався, чому `unique_ptr` не копіюється, а `shared_ptr` копіюється, і що станеться, якщо забути `std::lock_guard`. Жодного разу за ці дев'ятнадцять уроків тут не з'являлося ні слово про Claude Code, Copilot чи будь-який інший інструмент, що генерує код замість тебе. Це не забудькуватість — це був єдиний порядок, за якого курс не починав обманювати тебе з першого уроку. Якби ШІ з'явився в уроці 1, у тебе не було б жодної причини вчити решту дев'ятнадцяти — ти просто попросив би модель написати тренажер санскриту цілком, отримав би щось, що виглядає робочим, і жодного разу не зрозумів би, чому воно працює і в який момент перестане.

Тепер, коли позаду C++, вказівники, Qt, Unicode, потоки — є з чим порівнювати те, що видасть модель. Це і є вся різниця.

## Функція, яку не варто вигадувати заново

Замість вигаданого прикладу — розберемо справжню задачу з нашого SAMSKRTA. Користувачу незручно набирати `ā`, `ṣ`, `ṭ` — літери з діакритикою, яких немає на звичайній клавіатурі. Тому дозволяємо вводити слова спрощеною латиницею, за схемою Harvard-Kyoto (HK): довге «а» пишеться як `aa`, ретрофлексні приголосні — великими літерами. Потрібна функція, яка перетворить такий ввід на канонічний IAST.

Звучить як «заміни `aa` на `ā`, `sh` на `ś`, і так по колу». Настільки просто, що майже кожен, хто сідає писати це вперше — людина чи мовна модель, якщо попросити її про те саме найкоротшим формулюванням — приходить до одного й того самого короткого, але зламаного рішення:

```cpp
std::string normalizeNaive(const std::string& input, const std::string& scheme) {
    std::string out = input;
    std::transform(out.begin(), out.end(), out.begin(),
                   [](unsigned char c) { return static_cast<char>(std::tolower(c)); });

    if (scheme == "hk" || scheme == "itrans") {
        replaceAll(out, "aa", "ā");
        replaceAll(out, "sh", "ś");
        replaceAll(out, "t",  "ṭ");
        replaceAll(out, "s",  "ṣ");
        // ... ще кілька схожих рядків
    }
    return out;
}
```

Чотирнадцять рядків, кожен виглядає осмислено окремо. Збери, перевір на парі простих слів — спрацює. І всередині — три самостійні поломки, кожна непомітна, поки не почнеш шукати спеціально.

**Перша**: `input.toLower()` у самому першому рядку. У Harvard-Kyoto регістр має значення — велика `T` кодує ретрофлексний звук, мала `t` — звичайний. `toLower()` стирає цю різницю ще до того, як хоч одне правило встигло спрацювати. `normalize("Tapas", "hk")` і `normalize("tapas", "hk")` після цього дадуть однаковий результат, хоча за правилами HK це два різних слова. Уяви пошту, яка спершу стирає всі великі літери з адреси на конверті, а вже потім намагається зрозуміти, куди лист доставити.

**Друга**: умова `scheme == "hk" || scheme == "itrans"` виглядає так, ніби явно розрізняє дві схеми вводу. Насправді обидві гілки ведуть в один і той самий список замін. Параметр існує, приймає різні значення — і ні на що реально не впливає.

**Третя**: кожен `replaceAll()` змінює рядок, з яким працюватиме наступний виклик — вони виконуються строго послідовно, не одночасно. Поки правила не перетинаються підрядками, це непомітно. Але варто додати коротке правило, яке випадково стане підрядком уже наявного довшого і опиниться раніше за нього в списку, — і воно «з'їсть» шматок тексту, призначений для іншого правила. Сам код ніде не каже, що порядок цих рядків важливий — це існує тільки в голові того, хто їх розставив, і зникає безслідно за будь-якої невинної перестановки.

Правильна архітектура — таблиця правил замість каскаду замін, і на кожній позиції тексту вибір **найдовшого** підхожого правила (принцип **max-munch**, «найбільший шматок»), а не застосування правил одне за одним. Це новий постійний файл проєкту — `src/text/Translit.h`, поруч із `Devanagari.h` з уроку 14:

```cpp
// src/text/Translit.h
#pragma once

#include <string>
#include <vector>

namespace translit {

enum class Scheme { HK, ITRANS };

struct Rule {
    std::string from;
    std::string to;
};

// ===== Harvard-Kyoto: схема РЕГІСТРОЗНАЧУЩА =====
// Велика T кодує ретрофлексний звук, мала t — звичайний.
inline const std::vector<Rule>& rulesHK() {
    static const std::vector<Rule> table = {
        {"Th", "ṭh"}, {"Dh", "ḍh"},
        {"lR", "ḷ"},  {"RR", "ṝ"},
        {"A", "ā"},   {"I", "ī"},  {"U", "ū"},
        {"R", "ṛ"},   {"M", "ṃ"},  {"H", "ḥ"},
        {"T", "ṭ"},   {"D", "ḍ"},  {"N", "ṇ"},
        {"G", "ṅ"},   {"J", "ñ"},
        {"z", "ś"},   {"S", "ṣ"}
    };
    return table;
}

// ===== ITRANS: інша схема, інша таблиця, а не та сама гілка if =====
inline const std::vector<Rule>& rulesITRANS() {
    static const std::vector<Rule> table = {
        {"RRi", "ṛ"}, {"~N", "ṅ"}, {"~n", "ñ"},
        {"Sh", "ṣ"},  {"sh", "ś"},
        {"Th", "ṭh"}, {"Dh", "ḍh"},
        {"aa", "ā"},  {"ii", "ī"}, {"uu", "ū"},
        {"T", "ṭ"},   {"D", "ḍ"},  {"N", "ṇ"},
        {"M", "ṃ"},   {"H", "ḥ"}
    };
    return table;
}

inline const std::vector<Rule>& rulesFor(Scheme scheme) {
    return scheme == Scheme::HK ? rulesHK() : rulesITRANS();
}

// ===== Перетворення за принципом max-munch =====
// На кожній позиції беремо НАЙДОВШЕ правило, що підходить, а не перше-ліпше.
// Саме тому "Th" не розпадається на "T" + "h", а порядок рядків у таблиці
// ні на що не впливає.
inline std::string normalize(const std::string& input, Scheme scheme) {
    const auto& rules = rulesFor(scheme);
    std::string out;
    size_t i = 0;

    while (i < input.size()) {
        const Rule* best = nullptr;
        for (const auto& r : rules) {
            if (input.compare(i, r.from.size(), r.from) == 0) {
                if (!best || r.from.size() > best->from.size()) best = &r;
            }
        }
        if (best) {
            out += best->to;
            i += best->from.size();
        } else {
            out += input[i];
            i += 1;
        }
    }
    return out;
}

}  // namespace translit
```

Регістр тут ніхто не чіпає — таблиця для HK від початку містить окремі записи для великих і малих літер. Це вирішує всі три проблеми одним архітектурним рішенням: `toLower()` просто не потрібен, `scheme` нарешті вибирає по-справжньому різні таблиці, а не два імені для однієї гілки, і порядок рядків у таблиці перестає щось означати — правило вибирається за довжиною, а не за позицією в списку.

Вправа `exercises/ex20_review.cpp` ганяє обидві версії через одну таблицю тестів. Ось що вона друкує:


Подивись на перший блок наївної версії: `Tapas` і `tapas` перетворилися на **однакове** `ṭapaṣ`, хоча це два різні слова. Правильна версія тримає їх різними, як і має бути. У другому блоці параметр `scheme` не змінив нічого взагалі — обидва виклики дали `śanṭi`, тоді як правильна версія для HK і для ITRANS дає різні результати (в HK `sh` — це просто `s` плюс `h`, ніякого `ś` там немає).

І окрема історія про третій рядок таблиці тестів. Коли я вперше запустив цю вправу, вона показала **17 з 18**: рядок `kRRitam` дав `kṛtam` замість очікуваного `kṛitam`. Півхвилини я шукав помилку в коді — і не знайшов, бо її там не було. Помилка була в моєму очікуванні: правило ITRANS `RRi` поглинає літеру `i` цілком, тож `kRRitam` і мусить давати `kṛtam`. Таблиця приймання спіймала не баг у програмі, а **прогалину в моєму власному розумінні предметної області** — і саме тому її пишуть до генерації коду, а не після.

## Той самий код, який видала б модель

Ось у чому іронія, яку варто проговорити прямо. Той дванадцятирядковий каскад із `toLower()` на першому рядку — саме те, що видала б будь-яка мовна модель, якби ти попросив її «напиши функцію транслітерації з HK в IAST» без жодного уточнення. Не тому, що модель дурна, а тому, що це статистично найімовірніша відповідь на настільки коротке формулювання — той самий шлях найменшого опору, яким пішов би й ти сам, якби заздалегідь не знав, де тут пастка.

Різниця між тобою зараз і тобою на початку курсу не в тому, що ти пишеш код швидше за модель. Модель напише ці дванадцять рядків за секунду, ти набирав би їх хвилину. Різниця в тому, що ти, дивлячись на видане, за секунди впізнаєш у ньому три конкретні проблеми — а не просто відчуття «здається, працює».

Код сьогодні пишеться швидше, ніж читається. Написання перестало бути вузьким місцем розробки. Вузьким місцем стала перевірка. Це не привід ні для паніки, ні для захвату — привід переглянути, що саме тепер рідкісне й цінне в роботі програміста. Раніше цінність частково вимірювалася швидкістю перекладу зрозумілої задачі в синтаксично коректний код. Це вміння нікуди не зникло, просто воно більше не дефіцитне — модель робить те саме швидше майже завжди. Дефіцитним залишилося інше: вміння сказати, що саме має вийти, перш ніж просити когось це написати; вміння прочитати чужий (чи згенерований) код і за секунди розпізнати в ньому проблему рівня `toLower()`; і вміння провести межу між тим, що безпечно віддати генерації, і тим, де ціна помилки занадто висока. Ці три вміння — специфікація, межі, приймання — і організовують усе, що далі в цьому уроці.

## Специфікація важливіша за сам код

Модель не має доступу до контексту, що склався в тебе в голові за дев'ятнадцять уроків. Вона знає рівно те, що явно сказано в запиті — а те, що не проговорено, заповнюється не тим, що мав на увазі ти, а статистично найімовірнішим варіантом. Запит «зроби транслітерацію» не містить жодного з трьох уроків, які ми щойно розібрали — і тому відтворює рівно ті самі помилки.

Хороша специфікація для коду включає щонайменше:

- **Стек із точними версіями.** Не «проєкт на C++», а «C++20, Qt 6.5, CMake» — модель, що не знає точної версії, може запропонувати можливості, яких ще не існувало або які вже застаріли.
- **Куди має лягти код.** Якщо в проєкті є поділ на шари (`domain/`, `data/`, `ui/`) — прямо сказати: «цей клас живе в `domain/`, тому не може залежати від Qt Widgets ні в одному заголовку». Без цього найкоротший шлях до результату майже завжди проходить крізь межі, які ти вибудовував спеціально.
- **Точні сигнатури, якщо вони вже є.** Не «функція, що шукає слово за id», а `std::optional<Word> getById(WordId id)` — щоб не з'явився другий, трохи інакше виглядаючий спосіб робити те саме.
- **Правила іменування й мову коментарів.** Якщо в проєкті домовлено camelCase для змінних і українські коментарі — модель, навчена переважно на англомовному коді, без нагадування видасть коментарі англійською, і доведеться переписувати вручну.
- **Явну заборону на заглушки.** «Не залишай `TODO`, не повертай оптимістичне `true` там, де має бути реальна перевірка — якщо щось не реалізується повністю, скажи про це прямо, а не вдавай робочий код».
- **Перевірювані критерії приймання.** Конкретні пари «вхід → очікуваний вихід», а не розмите «зроби, щоб працювало правильно».

Прикладемо все це до нашого транслітератора:

> *«Реалізуй `translit::normalize(const std::string& input, translit::Scheme scheme)` у файлі `src/text/Translit.h` проєкту на C++20. Цей файл належить до текстового шару й не має залежати від Qt узагалі — тільки стандартна бібліотека. Вимоги, виведені з відомих дефектів наївної версії:*
> *1. НЕ приводь ввід до нижнього регістру — Harvard-Kyoto регістрозначуща схема, велика `T` кодує ретрофлексний звук, мала `t` — звичайний.*
> *2. `Scheme` — enum class мінімум із `HK` та `ITRANS`. Для кожної схеми — ОКРЕМА таблиця правил, не спільна гілка `if`.*
> *3. Пошук найдовшого підхожого правила на кожній позиції (max-munch), а не послідовність `replace()`.*
> *4. Таблиця тестів не менше 15 пар (вхід, очікуваний IAST), включно з випадком, де одне правило — префікс іншого.*
> *5. Жодних `TODO` без реальної реалізації — якщо щось не покрите, перелічи це явно.*
> *Стиль: camelCase, англійські ідентифікатори, українські коментарі.»*

Різниця між цим формулюванням і коротким «зроби транслітерацію» — кілька хвилин написання. Різниця в результаті — три класи помилок, яких просто не виникне.

Корисна звичка, перш ніж просити код: попросити модель спочатку перевірити саму специфікацію. «Перш ніж генерувати код за цим описом — перевір його на повноту. Чи є в ньому неоднозначності, які довелося б вирішувати на власний розсуд? Перелічи їх явно, не додумуй мовчки». Цей крок ловить недомовленості до того, як вони перетворяться на код із рішеннями, які ти не узгоджував.

## Що віддавати машині, а що писати самому

Хороша специфікація вирішує «як просити». Не вирішує раніше поставленого питання — чи варто взагалі просити саме це.

**Віддавати сміливо** — там, де помилка дешева й видно її швидко:
- Повторюваний репозиторій, якщо один такий уже написаний вручну як зразок стилю — наступний, для іншої таблиці, це механічне повторення того самого патерну з іншими іменами полів.
- Верстка екрана за зразком — дев'яносто відсотків такого коду це створення віджетів і підключення їх у layout за знайомим шаблоном; помилку видно візуально за секунду після запуску.
- Механічна рутина: гетери й сетери, тести за вже складеною людиною таблицею «вхід → очікуваний результат».
- Систематичний рефакторинг за чітким правилом на кшталт «заміни всі `QString gender` на `enum class Gender` скрізь, де це поле читається чи пишеться» — інструмент, що не втомлюється від одноманітності, тут надійніший за людину, яка вручну неминуче щось пропустить.

**Не віддавати** — там, де помилка дорога, і виявиться не одразу:
- Архітектурні рішення: правило «залежності лише вниз», поділ на шари. Модель, попрохана «додай функцію, яка робить X» без нагадування про шари, з високою імовірністю вирішить задачу найкоротшим шляхом — SQL-запитом прямо всередині обробника кліка, не тому що не знає про архітектуру, а тому що це найкоротший шлях до робочого на вигляд результату.
- Схему бази даних. Рішення додати чи змінити таблицю зачіпає вже накопичені дані реальних користувачів — спроєктувати схему може й модель, але оцінити наслідки для існуючих даних лишається відповідальністю людини, яка ці наслідки переживатиме, якщо щось піде не так.
- Інваріанти домену — на кшталт «`WordId` і `LessonId` не повинні бути взаємозамінними». Модель не зобов'язана і не може сама здогадатися, що порушення такого правила неприпустиме, якщо це не проговорено явно.
- Усе, де ціна помилки — тихе псування прогресу користувача, накопиченого місяцями, без будь-якого повідомлення про збій.

Межа тут не про складність коду, а про ціну помилки і про те, хто за неї відповідає.

## Як читати код, що виглядає правильним

Слово «обман» тут не про злий умисел моделі — вона не бреше в людському сенсі, вона генерує статистично найімовірніше продовження, схоже на розв'язання задачі, без розуміння, працює воно насправді чи ні. Для того, хто читає результат, різниця нерозрізнювана на швидкому погляді. Ось сім конкретних місць, куди варто дивитися — не абстрактні міркування, а пряме продовження трьох поломок транслітератора з початку уроку:

1. **Порядок операцій.** Для будь-якої послідовності перетворень одного значення — чи вплине результат попереднього кроку на наступний, і що станеться, якщо поміняти два сусідні кроки місцями.
2. **Тиха втрата інформації.** `toLower()` перед регістрозначущими правилами — окремий, особливо підступний випадок: втрата ховається на рядку, який виглядає невинно.
3. **Оптимістичні заглушки.** Функція, що повертає `true` чи порожній успішний результат, нічого реально не зробивши. Перевірка: прочитай тіло буквально і спитай, за яких умов вона повернула б негативний результат прямо зараз.
4. **Коментарі-обіцянки.** «Обробимо пізніше», «поки так» — не проблема сама по собі, проблема в тому, що такі фрази губляться в потоці читання, якщо не привчити себе зупинятися саме на них.
5. **Межі буферів.** Перевірка розміру на початку функції створює ілюзію захищеності всього методу, хоча реально захищає лише перші кілька звернень.
6. **Ресурси без гарантованого вивільнення.** `new` без `delete` на всіх шляхах виходу — перевір явно шляхи через ранній `return` чи виняток.
7. **Unicode.** Модель за замовчуванням вважає, що символ дорівнює одній кодовій точці, якщо не сказано інше — і це ламається саме на деванагарі, як ти вже бачив в уроці 14.

Тести — не альтернатива цьому чек-листу, а його продовження в часі. Тест, що зафіксував «регістр у HK-схемі не повинен губитися», дозволяє потім сміливо рефакторити код навколо нього — тест або підтвердить, що інваріант цілий, або негайно повідомить про порушення, без потреби перечитувати весь код вручну.

Модель, явно спрямована на конкретний список, помічає власну помилку частіше, ніж при розмитому початковому запиті: «перш ніж я прийму цей код — перевір його сам за сімома пунктами: порядок операцій, тиха втрата інформації, оптимістичні заглушки, коментарі-обіцянки, межі буферів, вивільнення ресурсів, коректна обробка не-ASCII тексту. За кожним — явно «ризик є» або «перевірено», не пропускай мовчки». Остаточне рішення все одно за тобою.

## Скільки це реально коштує

Візьмемо наш транслітератор. Ручне написання таблиці правил з max-munch, окремі таблиці для HK і ITRANS, відладка граничних випадків — реалістично, кілька годин зосередженої роботи для людини, що вже знайома з темою, але не писала саме це раніше. Через специфікацію й генерацію: написання специфікації — хвилини, якщо вимоги вже зрозумілі заздалегідь (а вони зрозумілі — ми щойно самі знайшли ці дефекти); генерація — секунди; приймання за чек-листом із семи пунктів — десять-двадцять хвилин уважного читання плюс прогін тестової таблиці. Разом — на порядок менше часу, але за однієї обов'язкової умови: специфікацію писала людина, яка вже розуміє предметну область достатньо, щоб перерахувати в ній заздалегідь знайдені пастки.

Виграш від ШІ не однаковий по всій поверхні проєкту. Він максимальний там, де задача архітектурно складна, але вже десь розв'язана раніше (транслітерація — відома, вивчена область), або механічно об'ємна, але концептуально проста (введення даних за готовим списком). Мінімальний — там, де рішення унікальне для конкретного проєкту й вимагає судження, що не виводиться із загальних патернів.

Звідси й **правило трьох**: одна модель пише код за специфікацією. Друга — в окремій, незалежній розмові, що не бачила першої, — проводить приймання за чек-листом. Третя — резервний варіант, якщо перші дві розходяться в думках. Чому не можна попросити ту саму модель у тому самому діалозі перевірити щойно написане нею ж: модель несе «інерцію» вже прийнятих у цій розмові рішень, і попросити її саму знайти помилку статистично частіше закінчується підтвердженням уже зробленого вибору («так, усе вірно, я все продумав»), ніж реальним виявленням проблеми. Незалежний контекст дивиться на код свіжим поглядом — тим самим способом, яким людське рев'ю ефективніше за самоперевірку автора власного коду.

Інструменти тут теж не взаємозамінні. Агентні інструменти прямо в терміналі розробки (Claude Code, Aider, Cline) мають доступ до файлової системи проєкту й можуть самі запускати збірку та тести, ітеруючи без постійної участі людини — добре для задач із чітким автоматично перевірюваним критерієм: зібралося чи ні, тести пройшли чи ні. Покрокові інструменти на кшталт Copilot чи Cursor, що вимагають підтвердження кожної зміни — доречніші там, де критерій успіху суб'єктивний і потребує архітектурного судження з попереднього розділу. Локальні моделі, що працюють на власному залізі без відправки коду на сторонній сервер — окремий варіант там, де код містить комерційну таємницю; вибір між хмарним і локальним варіантом — питання вартості й конфіденційності, а не завжди якості результату.

## Що з цим робити далі

Ти пройшов курс із двадцяти уроків. Тепер ти знаєш, як влаштований C++ від синтаксису до пам'яті, як працювати з Qt, Unicode, багатопотоковістю — і як читати код, який лише виглядає правильним. Це і є той фундамент, без якого «вайб-кодинг» — просто ганебна вистава для мавпи з кнопкою: людина тисне «згенеруй» і не здатна відрізнити результат від ілюзії результату. З цим фундаментом те саме вайб-кодування — заслужений, справжній прискорювач.

Якщо хочеш побачити, як усі двадцять уроків складаються в один живий проєкт — повна версія книги (77 розділів) уже існує, і саме розділи 72–76 розгортають усе з цього уроку набагато повільніше й на більшій кількості прикладів. Розділ 77 книги пропонує ще одну корисну звичку насамкінець: відкрити `git log --oneline --reverse` власного проєкту й пройтися по ньому одним поглядом, від першого коміту до останнього — це чесніший підсумок пройденого шляху, ніж будь-який чужий текст, включно з цим.

---

**Питання для самоперевірки**

1. Чому наївний транслітератор із `toLower()` на першому рядку — це майже напевно те, що видала б і мовна модель на короткий запит «зроби транслітерацію HK в IAST»? Це говорить про те, що модель дурна, чи про щось інше?
2. Яка з трьох поломок транслітератора (`toLower()`, ілюзорний параметр `scheme`, залежність від порядку `replace()`) найважче помітна при побіжному читанні коду? Чому саме вона?
3. Наведи приклад із власного (навчального) проєкту SAMSKRTA, де помилку безпечно віддати генерації, і приклад, де ні. Що саме визначає різницю — складність коду чи щось інше?
4. Чому не можна попросити ту саму модель у тому самому діалозі перевірити код, який вона щойно написала? Що таке «правило трьох»?
5. *(з підступом)* Специфікація для `translit::normalize` явно забороняє `TODO` і заглушки. Що станеться з якістю згенерованого коду, якщо цю вимогу прибрати з промпту, а решту залишити без змін?
6. Додай у таблицю тестів рядок, де очікуваний результат ти виводиш сам із правил HK, не заглядаючи в код. Запусти. Якщо не збіглося — з'ясуй, помилився ти чи програма, і опиши, як саме ти це встановив.
