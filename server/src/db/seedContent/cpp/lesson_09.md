# Урок 9. Синглтон Database: хто вимикає світло

## Філософське питання на старті

Уяви, що в тебе вдома десять вимикачів, і кожен керує однією й тією самою лампочкою. Увімкнув перший — засвітилася. Увімкнув другий — теж світиться. Вимкнув перший — згасла. Дивно? Ще б пак. Але саме так працює програма, де можна створити скільки завгодно екземплярів бази даних, файлу налаштувань, логгера — речей, які **мають бути одні**.

У програмуванні це називається **синглтон** (singleton) — патерн, що гарантує: клас має лише один екземпляр, і до нього є глобальна точка доступу. Це один із найстаріших і найсуперечливіших патернів. Його або обожнюють, або ненавидять. Правда, як зазвичай, десь посередині. Але в нашому SAMSKRTA він ідеально підходить для класу `Database` — справді має бути один на всю програму.

## Чому Database має бути один

Уяви наш тренажер. В одному вікні — словник. В іншому — список слів для повторення. У третьому — статистика. У четвертому — налаштування. Усі ці вікна хочуть читати й писати в ту саму базу даних: список слів, прогрес користувача, налаштування. Якщо в кожному вікні буде свій екземпляр `Database` — вони не побачать зміни один одного. Одне вікно додало слово, інше про це не знає. Хаос. Саме тому `Database` має бути **один-єдиний**, і всі повинні звертатися до того самого екземпляра.

## Код уроку

Це `src/data/Database.h` — ще один постійний файл нашого проєкту. Зберігає він тепер не голі рядки, а `Word` з уроку 8 (`src/domain/Word.h`) — це і є той самий тип, яким `WordCard` в уроці 10 користуватиметься напряму, а лінійний `m_words` тут — тимчасове сховище: в уроці 15 воно обросте індексом для швидкого пошуку, а в уроці 16 — навчиться переживати перезапуск програми.

```cpp
// src/data/Database.h
// Синглтон Мейєрса: один екземпляр бази на всю програму.
// Заголовок. Сам по собі не збирається — його підключають інші файли.
#pragma once

#include <iostream>
#include <vector>
#include <mutex>
#include "../domain/Word.h"

// ===== Клас Database — синглтон Мейєрса =====

class Database {
public:
    // Забороняємо копіювання
    Database(const Database&) = delete;
    Database& operator=(const Database&) = delete;

    // Головний метод доступу до єдиного екземпляра
    static Database& instance() {
        // static всередині функції — ініціалізується ЛИШЕ при першому виклику
        // і живе до кінця програми
        static Database db;
        return db;
    }

    // Робота з даними
    void addWord(Word word) {
        std::lock_guard<std::mutex> lock(m_mutex);
        word.id = ++m_nextId;
        m_words.push_back(std::move(word));
    }

    std::vector<Word> allWords() const {
        std::lock_guard<std::mutex> lock(m_mutex);
        return m_words;  // повертаємо копію, щоб не давати прямий доступ
    }

    size_t count() const {
        std::lock_guard<std::mutex> lock(m_mutex);
        return m_words.size();
    }

private:
    // Конструктор і деструктор приватні
    Database() {
        std::cout << "[Database] створено (один раз)\n";
    }
    ~Database() {
        std::cout << "[Database] знищено (один раз, у кінці програми)\n";
    }

    mutable std::mutex m_mutex;  // для потокобезпеки (урок 17)
    std::vector<Word> m_words;
    int m_nextId = 0;
};

```

Знову, як і в уроці 8, заголовок на цьому закінчується: він описує, **що таке база даних**, і не запускає нічого. Три «вікна», які до неї звертаються, живуть у вправі `exercises/ex09_database.cpp`:

```cpp
// exercises/ex09_database.cpp
// Три "вікна" програми звертаються до однієї бази.
// Збери разом із проєктом: cmake --build build
// Запусти:                 ./build/ex09_database

#include "../src/data/Database.h"

void mainWindow() {
    auto& db = Database::instance();
    db.addWord(Word("धर्म", "dharma", "закон, обов'язок", 2));
    db.addWord(Word("कर्म", "karma", "дія, вчинок", 3));
    std::cout << "[mainWindow] зараз у базі: " << db.count() << "\n";
}

void reviewWindow() {
    auto& db = Database::instance();
    db.addWord(Word("सत्य", "satya", "істина", 1));
    std::cout << "[reviewWindow] зараз у базі: " << db.count() << "\n";
}

void settingsWindow() {
    auto& db = Database::instance();
    std::cout << "[settingsWindow] бачу: " << db.count() << "\n";

    for (const auto& w : db.allWords()) {
        std::cout << "  [" << w.id << "] " << w.devanagari
                  << " (" << w.transliteration << ")\n";
    }
}

int main() {
    std::cout << "Програма почалася\n\n";

    mainWindow();
    reviewWindow();
    settingsWindow();

    std::cout << "\nПрограма завершується\n";
    return 0;
}
```

Зверни увагу, що `ex09_database.cpp` підключає тільки `Database.h`, а `Word` йому доступний — бо `Database.h` сам підключив `Word.h`. Це і є та ситуація, заради якої в уроці 8 з'явився `#pragma once`: якби вправа підключила обидва заголовки, `Word` прочитався б двічі, і без захисту компілятор зупинився б.

Вивід:

```
Програма почалася

[Database] створено (один раз)
[mainWindow] зараз у базі: 2
[reviewWindow] зараз у базі: 3
[settingsWindow] бачу: 3
  [1] धर्म (dharma)
  [2] कर्म (karma)
  [3] सत्य (satya)

Програма завершується
[Database] знищено (один раз, у кінці програми)
```

Прочитай цей вивід уважно, бо в ньому весь урок.

`[Database] створено` надрукувалося **один раз**, і не на початку програми, а тільки коли `mainWindow` уперше попросив `instance()`. Рядок «Програма почалася» вийшов раніше — база на той момент ще не існувала. Це і є **ледача ініціалізація**: об'єкт створюється в мить першої потреби, а не при старті.

Далі три різні функції, жодна з яких нічого не знає про інші, бачать одні й ті самі дані: `mainWindow` додала два слова, `reviewWindow` побачила їх і додала третє, `settingsWindow` побачила всі три з наскрізними номерами 1, 2, 3. Номери роздає сама база через `++m_nextId`, і саме тому вони не повторюються — лічильник теж один на всіх.

`[Database] знищено` вийшло **після** «Програма завершується». Це важлива деталь: статичний об'єкт усередині функції знищується не в кінці `main`, а після нього, разом з іншими статичними об'єктами програми. Тому в деструкторі синглтона не можна покладатися на інші глобальні об'єкти — вони можуть бути вже мертві.

Розберемо, що тут відбувається.

**`static Database db` всередині функції `instance()`** — це так званий **«синглтон Мейєрса»**, названий на честь Скотта Мейєрса, який його популяризував. Магія в тому, що `static` всередині функції ініціалізується **лише при першому виклику** і живе до кінця програми. Більше того, з C++11 ця ініціалізація гарантовано потокобезпечна — компілятор сам подбає, щоб у багатопотоковому середовищі не вийшло двох екземплярів через гонку.

**`Database(const Database&) = delete`** — забороняємо копіювання. Без цього хтось міг би написати `Database db2 = Database::instance();` і отримати другий екземпляр. З `= delete` компілятор просто не дасть такого коду скомпілюватися. Це як замок на дверях: фізично можна зламати, але мовний контракт каже «не можна».

**Приватний конструктор** — ще один рівень захисту. `Database db;` у звичайному коді не скомпілюється, бо конструктор `private`. Створити екземпляр можна тільки через `instance()`. Це, власне, і робить клас синглтоном: контрольована точка створення.

**`mutable std::mutex m_mutex`** — м'ютекс, який можна заблокувати навіть у `const`-методах. `mutable` — маленьке слово, яке каже компілятору «це поле можна змінювати навіть у константному контексті». Це не зовсім чисто з точки зору дизайну (бо `const` обіцяє «не змінюй», а м'ютекс змінюється), але для потокобезпеки — необхідність. Поки що не переймайся цим, урок 17 розбере детально.

**`std::lock_guard<std::mutex> lock(m_mutex)`** — RAII-обгортка для м'ютекса. Конструюємо — м'ютекс блокується. Виходимо з функції (навіть через виняток) — `lock_guard` знищується, м'ютекс розблокується. Це безпечніше, ніж `mutex.lock()` і `mutex.unlock()` вручну, бо другий може не викликатися при винятку. Докладніше в уроці 17, поки просто запам'ятай шаблон.

**`db.allWords()` повертає копію вектора, а не посилання** — це свідоме рішення. Якщо повернути посилання, то клієнт зможе змінити вектор поза м'ютексом, і потокобезпека розсиплеться. Повертаючи копію, ми кажемо «ось тобі знімок стану на зараз, роби з ним що хочеш». Так, це трохи повільніше, але безпечно.

## Де синглтон уже працює навколо тебе

**Qt у повній мірі використовує синглтон-патерн.** `QApplication` — синглтон (один на всю програму), `QCoreApplication::instance()` — точка доступу. `QSettings` — синглтон для роботи з налаштуваннями. Коли ти пишеш `QSettings settings;` — це насправді `QSettings& settings = QSettings::instance();` під капотом. `QFontDatabase` — теж синглтон, бо система шрифтів одна.

**Бібліотека SDL** (для мультимедіа, на ній побудований Valve Source Engine) має `SDL_Init()` і `SDL_Quit()` — функції, що створюють і знищують глобальний стан. Це старий C-стиль синглтона, без класів, але з тією самою ідеєю.

**У Chromium** (а значить, у Chrome, Edge, Brave) — `BrowserContext`, `ProfileManager`, `PrefService` — усе це синглтони або їх варіації. У них навіть є спеціальний макрос `SINGLETON` і документація про те, як правильно писати синглтони, щоб не нарватися на проблеми з тестуванням.

**Чому синглтони критикують**: вони ускладнюють тестування. Коли в тебе є клас, який залежить від `Database::instance()`, ти не можеш підставити тестову базу замість справжньої, бо `instance()` повертає завжди одне й те саме. Рішення: передавати залежності явно (dependency injection) або використовувати інтерфейси. Але для нашого навчального проекту синглтон — оптимальний вибір, бо в нього не буде юніт-тестів у звичному розумінні.

**Аналогія з бібліотекою**: у бібліотеці один каталог. Кілька читачів можуть звернутися до нього одночасно — і всі побачать одну й ту саму колекцію книг. Каталог не можна скопіювати (єдиний екземпляр), не можна створити паралельно (один на всю бібліотеку), не можна знищити посеред робочого дня (живе до закриття). Синглтон — це каталог бібліотеки в архітектурі програми. Всі читачі (вікна, модулі) працюють через одну точку доступу, і всі бачать одне й те саме.

## Куди це веде далі

**Синглтон Мейєрса** (наш вибір) — простий, безпечний, ледачий (створюється при першому виклику). Альтернативи:

**Глобальний об'єкт**:
```cpp
Database g_database;  // створюється при старті програми
```
Мінус: створюється завжди, навіть якщо не потрібен. Може спричинити проблеми з порядком ініціалізації (якщо інші глобальні об'єкти хочуть до нього звернутися під час своєї ініціалізації).

**Передача через параметри** (dependency injection):
```cpp
class ReviewWindow {
    Database& m_db;
public:
    explicit ReviewWindow(Database& db) : m_db(db) {}
};
// У main: Database db; ReviewWindow rw(db);
```
Плюс: легко тестувати (підставити mock-базу). Мінус: треба тягати `Database&` скрізь, де він потрібен. У Qt, наприклад, `QSqlDatabase` передається через імена з'єднань — компромісний варіант.

**Шаблон Service Locator**:
```cpp
class ServiceLocator {
    static Database* s_database;
public:
    static Database& db() { return *s_database; }
    static void setDatabase(Database* db) { s_database = db; }
};
```
Гнучкіший за синглтон, але й складніший. Використовується у великих проектах, де потрібна тонка настройка того, який саме екземпляр використовується.

## Питання для самоперевірки

1. Додай у `Database` метод `bool removeWord(int id)`, який видаляє слово за `id` і повертає `true`, якщо воно було.
2. Чому конструктор і деструктор `Database` зроблені `private`? Що буде, якщо зробити їх `public`?
3. Спробуй написати `Database db2;` у `main`. Що каже компілятор? Чому?
4. Поясни, чому `static Database db` всередині `instance()` безпечніший за `static Database g_db;` як глобальну змінну.
5. Додай у `Database` лічильник — скільки разів до неї звернулися через `instance()`. Виводь це число перед завершенням програми.
