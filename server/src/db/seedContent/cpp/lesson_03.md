# Урок 3. Числа, які брешуть

Ти впевнений, що знаєш, що таке число. Два плюс два — чотири. Одна десята плюс дві десятих — три десятих. Все просто, ми вчили це в дитячому садку. А тепер сядь, будь ласка, бо комп'ютер з тобою не згоден, і він має рацію.

Спробуй цей код:

```cpp
#include <iostream>
int main() {
    double a = 0.1;
    double b = 0.2;
    std::cout << (a + b) << std::endl;
}
```

Збери, запусти. Ти очікував `0.3`. Ти побачив щось на кшталт `0.30000000000000004`. Це не баг. Це не помилка твого компілятора, не помилка твоєї операційної системи, не змова Microsoft проти тебе особисто. Це фундаментальна властивість двійкової системи числення, і вона впливає на кожну серйозну програму, яка рахує гроші, фізику, координати, прогрес учня. Якщо ти не розумієш, що тут відбувається, одного дня ти витратиш тиждень на пошук багу, якого не існує. Тому розбираємося зараз, поки дешево.

## Чому 0.1 не дорівнює 0.1

Люди рахують десятками — десять пальців, десять цифр, все логічно. Комп'ютер рахує двійками — у нього тільки «так» і «ні», «струм тече» і «струм не тече». Тому все, що ти пишеш, перед збереженням переводиться з десяткової в двійкову систему. І ось тут починається неприємне.

Деякі десяткові дроби в двійковій системі стають нескінченними. Класичний приклад — одна третина в десятковій: `0.3333...`, скільки б знаків не писав, точно не вийде. Точно так само `0.1` у двійковій — нескінченний дріб. Комп'ютер змушений його обірвати на якомусь біті (зазвичай 52-му для `double`), і виходить число, яке **майже** рівне 0.1, але не зовсім. Додай два таких майже-числа — похибка подвоїться і стане видимою.

Це не специфічно для C++. У Python те саме: `0.1 + 0.2` дає `0.30000000000000004`. У JavaScript, відомому своєю «дивною» математикою, теж саме. Це одна з тих речей, які об'єднують усіх програмістів світу, незалежно від мови. Як дощ у Лондоні — він буде, нічого не вдієш, бо стандарт подання дійсних чисел (IEEE 754) — один на всіх, і C++, і Python, і JavaScript просто йому підкоряються.

## Практичний наслідок: ніколи не порівнюй `==`

Якщо числа неточні за визначенням, то перевірка `if (sum == 0.3)` майже завжди поверне `false`, навіть коли за змістом має бути `true`. Це класична пастка новачків. Запам'ятай правило, написане кров'ю багатьох попередників:

```cpp
// ПОГАНО
if (a + b == 0.3) { /* ніколи не спрацює */ }

// ПРАВИЛЬНО
if (std::abs(a + b - 0.3) < 0.0001) { /* "досить близько" */ }
```

Другий варіант — «з допуском». Ми не питаємо «це точно рівно?», ми питаємо «це досить близько, щоб вважати рівним?». Розмір допуску (`0.0001`) залежить від задачі: для піксельних координат — `0.5`, для фінансів — не такий, але для фінансів ти взагалі не повинен використовувати `double`, про це нижче.

## Числа не тільки в десятковій формі

Один і той самий байт можна записати в коді по-різному — `255`, `0xFF`, `0377`, `0b11111111` — і всі чотири варіанти означають рівно те саме число, просто по-різному записане у вихіднику:

```cpp
int decimal     = 255;       // десяткове — за замовчуванням
int hexadecimal = 0xFF;      // шістнадцяткове — префікс 0x
int octal       = 0377;      // вісімкове — просто провідний нуль
int binary      = 0b11111111; // двійкове — префікс 0b, з C++14
std::cout << decimal << " " << hexadecimal << " " << octal << " " << binary << "\n";
// надрукує 255 255 255 255 — система числення існує тільки в тексті коду, не в пам'яті
```

Шістнадцятковий запис особливо поширений, бо один шістнадцятковий розряд — це рівно чотири біти, а два розряди — рівно один байт (`0xFF` — байт, повністю заповнений одиницями). Саме тому кольори у вебі пишуть як `#FF5733`, а адреси пам'яті в дебагері компілятор показує в hex, а не в десятковій системі — так простіше на око бачити межі байтів.

## Код уроку

Це наша перша вправа в дереві проєкту — `exercises/ex03_numbers.cpp`. Створи файл, а в `CMakeLists.txt` допиши рядок поруч із тим, що вже там є:

```cmake
add_executable(samskrta      src/main.cpp)
add_executable(ex03_numbers  exercises/ex03_numbers.cpp)
```

Числа тут не абстрактні. Це рівно ті величини, з яких за п'ять уроків складеться структура `Word`: рівень складності слова, скільки разів його показували, точність відповідей — і інтервал, через який слово треба показати знову. Тренажер санскриту — це, по суті, машина, яка вважає ці числа. Тому кожна пастка з цього уроку рано чи пізно вилізе саме в ньому.

```cpp
// exercises/ex03_numbers.cpp
// Збери разом із проєктом: cmake --build build
// Запусти:                 ./build/ex03_numbers

#include <iostream>
#include <iomanip>   // std::setprecision
#include <string>    // std::string — щоб побачити, скільки він важить
#include <limits>    // std::numeric_limits
#include <cmath>     // std::abs, std::isnan, std::isinf, std::exp
#include <cstdint>   // int32_t, int64_t
#include <numbers>   // std::numbers::e — C++20

int main() {
    // ===== Частина 1: інтервали повторення додаються не так, як ти думаєш =====
    // Слово першого рівня показуємо через 0.1 доби, другого — через 0.2 доби.
    double stepLevel1 = 0.1;
    double stepLevel2 = 0.2;
    double together   = stepLevel1 + stepLevel2;

    std::cout << std::setprecision(20);
    std::cout << "0.1 + 0.2       = " << together << "\n";
    std::cout << "дорівнює 0.3?     " << (together == 0.3 ? "так" : "ні") << "\n";
    std::cout << "різниця менша за 0.0001? "
              << (std::abs(together - 0.3) < 0.0001 ? "так" : "ні") << "\n\n";
    std::cout << std::setprecision(6);

    // ===== Частина 2: скільки байтів важить одне слово словника =====
    std::cout << "Розміри типів, з яких складається слово (у байтах):\n";
    std::cout << "  int         (рівень складності) : " << sizeof(int)         << "\n";
    std::cout << "  int         (лічильник показів) : " << sizeof(int)         << "\n";
    std::cout << "  bool        (чи вивчене)        : " << sizeof(bool)        << "\n";
    std::cout << "  std::string (сам рядок)         : " << sizeof(std::string)
              << "   <- і це БЕЗ самих символів\n";
    std::cout << "  double      (точність)          : " << sizeof(double)      << "\n\n";

    // ===== Частина 3: до якого числа взагалі вміє рахувати int =====
    constexpr int32_t maxInt = std::numeric_limits<int32_t>::max();
    std::cout << "Межі int: від " << std::numeric_limits<int32_t>::min()
              << " до " << maxInt << "\n";
    std::cout << "Якщо в int складати мілісекунди навчання, вистачить на "
              << maxInt / 1000.0 / 60.0 / 60.0 / 24.0 << " доби чистого часу\n";
    std::cout << "По 40 хвилин на день це "
              << maxInt / 1000.0 / 60.0 / 40.0 / 365.0 << " роки — досяжно для впертого учня\n\n";

    // ===== Частина 4: переповнення лічильника часу =====
    int totalMs = 2000000000;         // накопичено за ~2.5 роки занять
    int nextHalfYear = 500000000;     // ще пів року в тому самому темпі
    int afterHalfYear = totalMs + nextHalfYear;
    std::cout << "2000000000 + 500000000 = " << afterHalfYear
              << "  (очікувалось 2500000000)\n";
    std::cout << "той самий додаток в int64_t = "
              << static_cast<int64_t>(totalMs) + nextHalfYear << "\n\n";

    // ===== Частина 5: точність відповідей для слова, яке ще не питали =====
    double correct  = 0.0;   // жодної правильної відповіді
    double answered = 0.0;   // слово щойно додали, його ще не питали
    double accuracy = correct / answered;
    std::cout << "Точність нового слова (0/0) = " << accuracy
              << "  (nan? " << std::isnan(accuracy) << ")\n";
    std::cout << "accuracy == accuracy ?        "
              << (accuracy == accuracy ? "так" : "ні") << "  <- nan не рівний сам собі\n";

    double answers = 3.0;
    double seconds = 0.0;                  // секундомір ще не встиг цокнути
    double answersPerSecond = answers / seconds;
    std::cout << "Швидкість 3 / 0.0            = " << answersPerSecond
              << "  (inf? " << std::isinf(answersPerSecond) << ")\n\n";

    // ===== Частина 6: крива забування, на якій тримається весь тренажер =====
    // Еббінгауз: частка того, що пам'ятаєш, R = e^(-t/S)
    const double stability = 2.0;   // доби
    std::cout << "Крива забування R = e^(-t/S), S = " << stability << " доби:\n";
    for (int day = 0; day <= 8; day += 2) {
        double retention = std::exp(-day / stability);
        std::cout << "  t = " << day << "  ->  R = "
                  << std::fixed << std::setprecision(1) << retention * 100.0 << "%\n"
                  << std::defaultfloat << std::setprecision(6);
    }
    std::cout << "основа цієї формули, std::numbers::e = " << std::numbers::e << "\n";
}
```

Вивід (MSVC 19.44, Windows x64 — на GCC частина чисел відрізнятиметься, і нижче сказано, які саме):


Розберемо по частинах.

`std::setprecision(20)` — кажемо `cout`-у друкувати 20 значущих цифр, а не звичайні 6. Без цього рядок показав би рівно `0.3`, і похибка сховалася б за округленням. Це як читати дрібний шрифт на упаковці ліків: треба піднести близько, щоб побачити. Зверни увагу на другий рядок виводу: два інтервали повторення, які **на папері** дають рівно `0.3`, у пам'яті дають `0.30000000000000004441`, і перевірка `== 0.3` чесно каже «ні». Якби планувальник повторень порівнював інтервали через `==`, він мовчки не спрацьовував би для частини слів.

`sizeof(std::string)` дорівнює 32 і **не залежить** від довжини рядка — це найчастіше непорозуміння в цьому виводі. Сам об'єкт `std::string` — це маленька службова структура: вказівник на дані, довжина, місткість (плюс невеликий вбудований буфер для коротких рядків). Самі символи лежать окремо в купі, і `sizeof` про них нічого не знає. На GCC/libstdc++ вийде 32, на Clang/libc++ теж 24–32 залежно від версії — конкретне число не універсальне, а от принцип «розмір об'єкта ≠ розмір даних» універсальний.

`std::numeric_limits<int32_t>::max()` — спосіб дізнатися максимальне значення типу, не шукаючи в таблиці, де `INT_MAX` дорівнює 2147483647. Працює для будь-якого числового типу. Я взяв тут `int32_t` замість простого `int` навмисно: `int` — це «принаймні 16 біт, на практиці зазвичай 32», а `int32_t` — «рівно 32 біти, інакше код не збереться». Коли число має вміститися у файл чи мережевий пакет, здогадки не годяться.

`int totalMs = 2000000000; int afterHalfYear = totalMs + 500000000;` — переповнення, і воно тут не вигадане для страху. Порахуй за виводом: 2.1 мільярда мілісекунд — це 24.8 доби чистого часу, тобто дві з половиною роки по 40 хвилин на день. Для тренажера, яким користуються роками, це не гіпотетична межа. Складаємо два числа, кожне з яких уже близьке до неї, — результат фізично не влізає в 32 біти й «обертається» у від'ємний `-1794967296`. Компілятор не видав ані помилки, ані попередження, програма не впала — просто з цієї миті статистика учня показує від'ємний час навчання. Для знакових типів у C++ це формально **невизначена поведінка**: стандарт дозволяє компілятору зробити взагалі що завгодно, а не тільки «обернути». Лікується одним символом — `int64_t` замість `int`, останній рядок цієї частини це й показує.

`correct / answered`, де обидва нулі, дає `nan` — і це найпідступніший рядок усього уроку. Слово щойно додали до словника, його ще жодного разу не питали, і формула «точність = правильні / усі відповіді» чесно ділить нуль на нуль. Для дійсних чисел ділення на нуль не кидає помилку: стандарт IEEE 754 визначає спеціальні значення `+inf`, `-inf` і `nan` («не число»). MSVC друкує його як `-nan(ind)`, GCC — як `-nan` або `nan`; форма запису різна, суть та сама. Пастка в іншому: `nan == nan` повертає `false`, бо `nan` за визначенням не рівний навіть самому собі. Якщо `nan` просочився в обчислення, він отруює все, до чого доторкнеться — середню точність по всьому словнику, сортування, вибір наступного слова, — і звичайний `==` його не знайде. Перевіряти треба спеціальними функціями: `std::isnan()`, `std::isinf()`. А правильне рішення в самому застосунку — не рахувати точність, поки `answered == 0`, а показувати «ще не питали».

`std::exp` і `std::numbers::e` — це та сама математика, заради якої тренажер узагалі існує. Крива забування Еббінгауза каже: частка запам'ятованого падає як `R = e^(-t/S)`, де `t` — час, `S` — стійкість сліду в пам'яті. Подивись на вивід: через дві доби від слова лишається 36.8%, через вісім — 1.8%. Саме тому повторення планують не рівномірно, а зі зростаючими проміжками — щоб ловити слово в момент, коли воно ось-ось випаде. З цієї формули в уроці 4 виросте `switch` по рівнях складності, а в уроці 8 — поле `difficultyLevel` у структурі `Word`.

Сама константа `e` має кумедну історію, яка дивує майже всіх, хто прийшов у C++ із мов із готовою математикою «з коробки»: математичних констант у мові довго не було зовсім — ні ключового слова, ні літерала, тільки старий макрос `M_E` з бібліотеки C, який на MSVC треба було окремо вмикати рядком `#define _USE_MATH_DEFINES` перед `<cmath>`. Тільки з C++20 з'явився нормальний спосіб — `constexpr`-константи `std::numbers::e`, `std::numbers::pi` та інші з заголовка `<numbers>`, без макросів і танців із визначеннями.

## Де це реально ламає системи

**Vancouver Stock Exchange, 1982.** Один із найцитованіших прикладів у книгах з чисельних методів: новий фондовий індекс перераховувався тисячі разів на день, і на кожному перерахунку результат **відкидав** зайві знаки після коми замість того, щоб округлювати — крихітна помилка, здавалося б, нижче порогу чутливості. За 22 місяці накопичених відкидань індекс, який мав бути близько 1098 пунктів, показував 520 — майже вдвічі менше за реальність. Виправили одним пересчетом за вихідні. Урок: помилка на кожному кроці менша за похибку заокруглення в одну цифру, помножена на мільйони кроків, перестає бути дрібницею.

**Boeing 787, 2015.** Федеральне авіаційне управління США видало директиву про реальну ваду генераторів літака: внутрішній програмний лічильник часу безперервної роботи переповнювався приблизно через 248 днів без перезавантаження, і всі чотири генератори одночасно йшли в аварійний режим — ризик повної втрати змінного струму на борту. Не через дійсні числа конкретно, а через той самий принцип: лічильник фіксованого розміру рано чи пізно переповнюється, якщо працює досить довго без скидання, і про це треба думати заздалегідь, а не сподіватися, що «до цього не дійде».

**Ігри**: рушії ігор люблять `float` для координат, бо він удвічі компактніший за `double` і процесор обробляє його швидше. А коли гравець пройде половину величезного світу і накопичиться похибка — його може телепортувати чи «затрясти» біля якоїсь віддаленої точки. Класичний «баг великих відстаней», знайомий розробникам відкритих світів (Minecraft у ранніх версіях, деякі великі карти на Unreal Engine) — не тому що float «зламаний», а тому що точності 7 значущих цифр не вистачає, коли координата стає шестизначною.

## Куди йти, якщо double не підходить

Для грошей і точних десяткових розрахунків — цілочисельні копійки (`int64_t priceInCents = 19999; // 199.99 грн`) — швидко, точно, без сюрпризів; або бібліотека Boost.Multiprecision з типом `cpp_dec_float_50`, якщо потрібні десятки значущих цифр ціною швидкості.

Для переповнення в цілих числах — прапорці санітайзерів компілятора (`-fsanitize=address,undefined` на GCC/Clang, `/RTC` на MSVC), які ловлять переповнення й невизначену поведінку під час виконання, а не мовчки пропускають її. Або просто вибір типу з запасом (`int64_t` замість `int`) там, де числа можуть вирости.

---

**Питання для самоперевірки**

1. Допиши у вправу підрахунок `0.1 + 0.2 + 0.3` і порівняй із `0.6`. Чому результати різні?
2. Запиши число `2147483647 + 1` у `int`. Що вийшло? Чому компілятор не попередив?
3. Напиши функцію `bool isEqual(double a, double b, double epsilon)`, яка порівнює два дійсних числа з допуском `epsilon`. Використай її замість `==` у першій частині вправи.
4. Поясни різницю між `inf` і `nan`. Як їх перевірити? Який із них з'явиться, якщо поділити кількість правильних відповідей на кількість заданих питань для слова, яке ще жодного разу не показували?
5. Допиши функцію `double accuracyOf(int correct, int answered)`, яка не дає `nan` ніколи: якщо `answered == 0`, вона має повернути щось осмислене. Придумай, що саме, і поясни свій вибір — це рішення потім вплине на те, як тренажер сортує слова.
6. Порахуй за формулою `R = e^(-t/S)`, через скільки діб від слова лишиться рівно половина (`R = 0.5`) при `S = 2`. Перевір відповідь кодом.
